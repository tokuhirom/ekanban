# 設計の記録

README がプロジェクトの方針と完成形を示すのに対し、この文書は **決めたことと、決めなかったこと** を残します。

**進行中の作業は [GitHub issues](https://github.com/tokuhirom/ekanban/issues) で管理します。** 「次に何をやるか」はここには書きません。以前あったフェーズ別のタスク一覧と受け入れ条件は、残っていたものを issue に移してから削除しました。

ここに残すのは、issue を 1 つ閉じても消えない種類のこと、つまり後から来た実装が従うべき制約と、同じ検討を二度しないための判断の記録だけです。

## 引き継ぐ設計の決まりごと

今後の実装が従うもの。破るときは、破る理由をここに書き足すこと。

- **期限は日付のみ**、`TEXT` の `'YYYY-MM-DD'` で持つ。時刻は持たない。必要になった時点で `due_time` を足す
- **絞り込みはカードを隠さず減光する。** 隠すとドロップの挿入位置が曖昧になり、D&D の意味が変わるため
- **並べ替えは一時的なビューではなく `position` の書き換え**として行う。見た目の位置と本来の位置が食い違わないようにする
- **履歴に残すのはカードのライフサイクルだけ**（`created` / `moved` / `archived` / `restored` / `deleted`）。カラム内の並べ替えと属性変更は残さない。既存データを遡って生成しない
- **Undo のスタックと `card_events` は共有しない。** 寿命（セッション / 永続）と目的（取り消し / フローの記録）が違う
- 保存はボード本体と履歴を 1 トランザクションで行い、失敗したらメモリ上の状態と `pending_events` の両方を捨てる
- **色だけに意味を持たせない。** アイコンか文言で必ず区別できるようにする
- **色は `ActiveTheme::theme()` から引く。** `rgb(0x…)` の直書きはユーザーが指定したタグの色だけに許す
- 入力欄・検索欄にフォーカスがある間はボードのショートカットを無効にし、IME とテキスト編集を優先する
- **アプリ独自のキーボードショートカットは `secondary-` で定義する。** `secondary` は macOS では Cmd、Linux と Windows では Ctrl になる。`cmd-` を使ってよいのは、macOS のシステムメニューの割り当て（`cmd-q` `cmd-h` `cmd-alt-h`）と、`Ctrl` を含む組み合わせ（`cmd-ctrl-*`）だけ。後者を `secondary-ctrl-*` にすると非 macOS で `Ctrl` が重なって潰れ、`secondary-s` や `secondary-f` と衝突する
- **グローバルホットキーが使えるのは macOS と X11 のセッションだけ。** Wayland にはアプリから使える共通の仕組みが無い。`global-hotkey` の X11 実装は使えない環境でも登録が成功したように見える（スレッドの生成しか確かめず、そのスレッドが死んでいても `register` が `Ok` を返す）ので、戻り値を信じずに環境変数で先に判定する。使えない環境ではメニュー項目を灰色にし、理由を文言に出す
- **グローバルホットキーは既定で登録しない。** ユーザーが割り当てて初めて有効になる。全画面でその組み合わせを奪うので、断りなく取ると、ほかのアプリが動かなくなった理由を追えなくなる。修飾キーを 1 つも含まない割り当ても同じ理由で受け付けない
- **登録できていない割り当てを保存しない。** 登録に失敗したらその場で理由を出し、設定は変更前のまま残す。起動のたびに黙って失敗する状態を作らない
- **クイックキャプチャの保存はボードの保存経路を通す。** キャプチャウィンドウから直接 SQLite を触らない。`save_lock` で守っている前提が崩れ、ボード側の非同期保存と競合する。`BoardView` に依頼すれば、カラムの末尾に足す・1 回の保存で永続化する・Undo の対象になる・`created` イベントが 1 件積まれる、がそのまま満たされる
- **矩形を保存するのはボードのウィンドウだけ。** キャプチャウィンドウは毎回画面中央に出す
- **クイックキャプチャ先はアプリ全体で 1 つ。** ボードごとには持たない。ボードを切り替えても入れ先が変わらないことが、この機能の使い勝手そのものだから。指しているボードやカラムが消えていたら黙って既定（開いているボードの先頭カラム）に戻す
- **開いていないボードへのキャプチャは Undo の対象にしない。** Undo のスタックは開いているボードのモデルが持つもので、開いていないボードの操作を積む場所がない。積める場所を作ると「Undo を押したのに画面が変わらない」状態を作ることになる
- **確認ダイアログは Undo の代わりではない。** 出すのは「Undo で戻せない」か「1 操作で複数件が消える」ものに限る。すべての削除に出すと、読まずに押す確認になって役に立たなくなる
- **常用しない操作を画面に常時出さない。** カードの操作は右クリックメニュー、カラムの操作は `…` メニューに集約する。`danger`（赤）はダイアログの確定ボタンとメニュー内の削除項目だけに使う
- カード表面の高さは、チェックリストの項目数のような可変の要素で変えない。ドラッグゴーストの大きさと挿入位置の判定が安定しなくなるため

## スコープ外

README の方針どおり、実装しません。

- クラウド同期、アカウント、サーバー通信
- 複数ユーザー、共有、権限管理
- 通知・リマインダー（期限は表示のみ。OS 通知は扱わない）
- Markdown レンダリング（説明はプレーンテキストのまま）
- 他ツールからのインポート（ID 衝突と重複解決が実質的に同期の設計になるため）

## 検討して入れないと決めたもの

Trello と OmniFocus を参照して洗い出した候補のうち、検討のうえ実装しないと決めたものです。「思いつかなかった」のではなく「判断した」ことを残すために書いています。

| 項目 | 判断の理由 |
| --- | --- |
| 開始日（`defer_date`） | Kanban では「まだ着手しない」を**カラムが表している**。Backlog / Someday というカラムがあるのに日付でも同じことを表すと状態の表現が二重になり、「Ready カラムにあるが開始日が来ていないカード」が何を意味するのか答えられない。減光の条件がすでに 3 つ（検索・タグ・期限）あり、4 つ目を足すと「なぜこのカードが暗いのか」が読めなくなる |
| 保存されたビュー（Perspective） | ヘッダがすでに混んでいる（検索・タグ・期限・アーカイブ）。個人の 1 ボードでタグ数個・カラム数個の規模なら、絞り込みを手で作り直すコストはそもそも低い。OmniFocus の Perspective が効くのはプロジェクト数百のスケールがあってこそ |
| フラグ（1 bit の重要マーク） | タグで完全に代用できる。欲しくなる理由は操作コストなので、カードのコンテキストメニューでタグを直接トグルできるようにして解決した |
| カードの複数選択 | 主用途である「Done をまとめて片付ける」は `archive_column` ですでに満たされている。複数選択の D&D はゴーストの見せ方と挿入枚数の表現が難しく、最重視の D&D の直感性を落とすリスクが実利に見合わない |
| カラムの折りたたみ | 折りたたんだ列への D&D の振る舞い（落とせないのか、ホバーで展開するのか、末尾固定で落とせるのか）がどれも今の一貫性から外れる。カラム 3〜5 個の現状では横スクロールに困っておらず、困っていない問題への対処になる |
| 見積ポイントと WIP のポイント制 | 個人ボードで見積の運用は続きにくく、空欄のまま放置されてポイント制が機能不全になる。枚数の粗さはむしろ「大きすぎるカードは分割しろ」という圧力として働く。加えて `card_events` が入ったので**実測のサイクルタイム**が取れる。見積は実測の代替なので、実測が取れるなら要らない |
| 添付ファイル・カバー画像 | ローカル専用なので絶対パスを持つだけで実装できるが、ファイルが移動・削除されたときの破綻の面倒を見る価値がこのアプリにはない |
| カレンダー / タイムラインビュー | D&D の落とし先がボードとカレンダーで二重になり、最優先の方針と正面から衝突する |
| コメント欄・アクティビティフィード | 単独ユーザーでは薄い。「いつ何が起きたか」は `card_events` が持つ |
| メニューバー常駐（ステータスバーアプリ） | 常駐の価値はクイックキャプチャと通知にあるが、前者は常駐なしの小窓として実装する方針にしたため常駐は要らず、後者はスコープ外。残るのは「ウィンドウを速く出す」だけで、Dock と `Cmd+Tab` で足りている。「アプリが起動している間しか効かない」が実際に不満になったら、そのときに再検討する |

### 撤回した判断

一度は入れないと決めたが、根拠が誤っていたので撤回したもの。

| 項目 | 撤回の理由 |
| --- | --- |
| グローバルホットキーのクイックキャプチャ | 見送りの理由は「macOS ではアクセシビリティ権限を要求することになる」「『アカウント、サーバー、権限を必要としない』という方針と合わない」の 2 つだったが、どちらも成り立っていなかった。前者は誤りで、macOS のグローバルホットキーは Carbon の `RegisterEventHotKey` で登録でき権限は要らない（権限が要るのは `CGEventTap` でキー入力そのものを覗く方式）。後者は README の引用が誤りで、方針は「アカウント、サーバー、**ネットワーク接続**を必要としない」であり権限のことは書いていない。実装は #11〜#14 |

## 前提が揃えば検討するもの

現時点では実装しません。前提が満たされたら再検討します。着手時期が決まっていないので issue にはしていません。

| 項目 | 前提 | 状況 |
| --- | --- | --- |
| 繰り返しカード | **明示的な「完了」の概念**。ekanban には今それがなく、Done カラムは慣習にすぎない。何を引き金に次を生成するかを定義できない。加えてバックグラウンド動作がないため、1 ヶ月起動しなければ日次カードが 30 枚生まれる。抑制の設計も要る | 未充足 |
| URL スキーム（`ekanban://board/1/card/12`） | **複数ボード**（形が決まらないと後で URL を壊す）。加えて登録方法が OS ごとに違い（macOS は `Info.plist`、Linux は `.desktop`、Windows はレジストリ）、既に起動中のアプリに URL を渡す単一インスタンス制御も要る | 複数ボードは充足。残るのは単一インスタンス制御。カード番号を出したので「番号を見たが飛べない」不満が実際に出たら着手する |
| 履歴の可視化（滞留・サイクルタイム・CFD） | **`card_events` のデータが十分に貯まること**。何を見たいかはデータを見てから決める | 記録は開始済み。判断はデータ待ち |

## 変更の完了条件

issue を閉じる前に、すべて満たしていること。

1. `cargo fmt --all -- --check` が通る
2. `cargo clippy --all-targets --all-features -- -D warnings` が通る
3. `cargo test --all-features` が通る
4. モデルの変更には `#[cfg(test)]` のユニットテストが付いている
5. スキーマの変更には、旧バージョンの DB を開くマイグレーションテストが付いている
6. 入力欄を追加・変更した場合は、日本語 IME での入力を実機で確認している
7. 表示を変更した場合は、macOS のライトとダークの両方で確認している
8. README の記述と食い違いが出ていない
