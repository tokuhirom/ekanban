## フェーズ 0: 基盤の是正

### 0-1. ID 採番を単調増加にする（課題 C1）

ボードごとに次の ID を保持し、削除では減らさない方式に変える。

- スキーマ v2 で `boards` に `next_card_id INTEGER NOT NULL DEFAULT 1` と `next_column_id INTEGER NOT NULL DEFAULT 1` を追加する
- 既存 DB のマイグレーション時に `MAX(id) + 1` で初期化する
- `Board` に `next_card_id` / `next_column_id` フィールドを持たせ、`add_card` / `add_column` はそこから採番して加算する

受け入れ条件:

- 「カードを 3 枚追加 → 3 枚目を削除 → 1 枚追加」で新しいカードの ID が 4 になるテストが通る
- 既存の `ekanban.sqlite3` を開いても ID が衝突しない

### 0-2. 保存を差分更新にする（課題 C2）

`save_board` の全削除・全挿入をやめる。

- `columns` / `cards` を `INSERT ... ON CONFLICT(id) DO UPDATE` で UPSERT する
- ボードに存在しない行だけを `DELETE FROM cards WHERE column_id IN (...) AND id NOT IN (...)` で消す
- 1 トランザクションで行う点は現状どおり維持する

受け入れ条件:

- 既存の round-trip テストがすべて通る
- 「カードを 1 枚移動して保存 → 別プロセスで読み直す」で `created_at` が保存前後で変わらないテストが通る（全削除・再挿入だと壊れやすい不変条件のため）

## フェーズ 2: 期限管理

### 2-0. 設計判断

**粒度は日付のみとする。** 時刻は持たない。

理由: Kanban のカードは「その日中にやる」単位で扱われることがほとんどで、時刻を持つとタイムゾーン変換・夏時間・「23:59 は今日か明日か」といった問題を、得られる価値に見合わないコストで抱え込むため。時刻付きリマインダーが必要になった時点で `due_time` を追加する後方互換な拡張余地は残る。

**保存形式は `TEXT` の `'YYYY-MM-DD'`。**

理由:

- 辞書順がそのまま日付順になるので `ORDER BY due_date` が素直に書ける
- `sqlite3` CLI で中身を直接読める
- タイムゾーンに依存しない絶対的な暦日として解釈できる
- `NULL` が「期限なし」を自然に表す

**依存の追加**: 「今日」をローカルタイムゾーンで求めるには std だけでは足りないため、`chrono`（0.4 系, `features = ["clock"]`）を追加する。日付の解析・整形・加算にも使う。追加時点の最新バージョンを確認すること。

### 2-1. スキーマ v3

```sql
ALTER TABLE cards ADD COLUMN due_date TEXT;
CREATE INDEX IF NOT EXISTS idx_cards_due_date ON cards(due_date);
```

- 既存行は `NULL`（期限なし）になり、後方互換
- `migrate()` のバージョン分岐に v3 を足す。v1 → v3 の一括適用と、v2 → v3 の差分適用の両方が通ること

### 2-2. モデル

```rust
// model.rs
pub struct Card {
    // ...
    pub due_date: Option<NaiveDate>,
}

impl Board {
    /// 期限を設定する。None で解除。変更がなければ false を返す。
    pub fn set_card_due_date(
        &mut self,
        card_id: CardId,
        due_date: Option<NaiveDate>,
    ) -> Result<bool, BoardError>;
}
```

- `add_card` は `due_date: None` で作る
- `update_card` のシグネチャは変えず、期限は別メソッドにする（編集ダイアログからは両方を呼ぶ）
- 不正な日付文字列は `BoardError::InvalidDueDate(String)` で弾く

### 2-3. 期限状態の判定

表示ロジックを純関数に切り出し、「今日」を引数で受け取る。テストで固定日付を渡せるようにするため、内部で現在時刻を読まないこと。

```rust
// model.rs
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum DueStatus {
    /// 期限切れ。超過日数を持つ。
    Overdue(i64),
    /// 今日が期限。
    Today,
    /// 期限が近い（残り 1〜3 日）。残日数を持つ。
    Soon(i64),
    /// それより先。
    Upcoming(i64),
    /// 期限なし。
    None,
}

pub fn due_status(due_date: Option<NaiveDate>, today: NaiveDate) -> DueStatus;
```

`Soon` の閾値 3 日は定数 `SOON_THRESHOLD_DAYS` として切り出し、後で設定可能にできるようにしておく。

### 2-4. カード上の表示

- カードのタイトル下に期限バッジを出す。期限が `None` のカードにはバッジを出さない（余白を増やさない）
- 表示文言は相対表現を優先し、絶対日付を併記する
  - `Overdue(n)` → 「n 日超過 (10/02)」
  - `Today` → 「今日 (10/05)」
  - `Soon(n)` → 「あと n 日 (10/07)」
  - `Upcoming(_)` → 「10/20」（同一年なら年を省略し、年をまたぐ場合のみ「2027/01/10」）
- 色は gpui-kit のテーマ色に対応づける。`Overdue` は danger、`Today` は warning、`Soon` は accent、`Upcoming` は muted
- 色だけに意味を持たせない。アイコンか文言で必ず区別できるようにする

### 2-5. 期限の編集 UI

既存の `CardEditor` に期限フィールドを足す。

- `YYYY-MM-DD` のテキスト入力（半角数字のみ、IME を通さない）
- クイック設定ボタン: 「今日」「明日」「今週末」「来週」「クリア」
- 不正な文字列はフィールド下に赤字でエラーを出し、保存ボタンを無効化する
- カレンダーピッカーはフェーズ 3 以降に回す。テキスト＋クイックボタンで実用に足りるため

### 2-6. 期限による並べ替えと絞り込み

**並べ替えは、一時的なビューではなく position を書き換える一回きりの操作にする。** カラムメニューの「期限順に並べ替える」を押すとカードの `position` を実際に書き換え、そのまま保存する。

理由: 並び順を一時的に差し替えると、ドラッグ＆ドロップの落とし先が「見た目の位置」なのか「本来の position」なのか曖昧になり、このアプリが最重視する D&D の直感性が壊れるため。

- 並べ替えキーは `(due_date が None は末尾, due_date 昇順, position 昇順)`
- 実行は Undo 対象にしたい（フェーズ 4 まではモデル上のロールバックのみ）

**絞り込み（「期限切れのみ」「今週まで」）は、カードを隠さず、非該当カードを減光して表示する。**

理由: カードを隠すと、隠れたカードをまたぐドロップの挿入位置が曖昧になるため。減光なら D&D の意味が変わらない。

### 2-7. テスト

- `due_status` の境界: 前日 / 当日 / 翌日 / 3 日後 / 4 日後、および `None`
- 年またぎ（12/31 と 1/1）と閏日（2/29）
- `set_card_due_date` が変更なしのとき `false` を返す
- DB の round-trip: 期限あり・期限なしの両方のカードを保存して読み直す
- マイグレーション: v1 の DB を開いて v3 になり、既存カードの `due_date` が `NULL` になる
- 日付文字列のパース失敗が `InvalidDueDate` になる

## フェーズ 3: 絞り込みと整理

### 3-1. 検索（実装済み）

- ヘッダに検索ボックスを置き、タイトルと説明を部分一致（大文字小文字・全角半角を区別しない）で検索する
- ヒットしないカードは 2-6 と同じく減光表示にする
- 日本語の検索語を扱うため、IME 確定後にのみ検索を走らせる

### 3-2. タグ / ラベル（実装済み）

- スキーマ v5 で `tags(id, board_id, name, color)` と `card_tags(card_id, tag_id)` の 2 テーブルを追加する
- カード上に色付きの小さなチップとして表示する
- タグによる絞り込みを 3-1 と同じ仕組みに載せる
- ヘッダからタグの追加・編集・削除、カード編集欄からタグの付け外しを行う

### 3-3. WIP 制限（実装済み）

- スキーマ: `columns.wip_limit INTEGER NULL`
- カラムヘッダに `3 / 5` のように現在枚数と上限を出す
- 上限を超えたらヘッダを警告色にする。**ドロップ自体は禁止しない**（作業の実態を隠さないため、Kanban の WIP 制限は警告に留めるのが定石）

### 3-4. アーカイブ（実装済み）

- スキーマ v6 で `cards.archived_at INTEGER NULL` を追加する
- 各カラムの「アーカイブ」でカードをまとめてアーカイブする操作を用意する
- カード単位のアーカイブにも対応する
- アーカイブ済みカードはボードに表示せず、別ビューから閲覧・復元できる
- 前提: フェーズ 0-1 の ID 採番（アーカイブしたカードの ID が新規カードに再利用されると復元時に衝突するため）

## フェーズ 4: 運用性

### 4-1. Undo / Redo

- ボードのスナップショットではなく、操作を表す enum（`MoveCard`, `EditCard`, `SetDueDate`, ...）のスタックとして持つ
- `Ctrl+Z` / `Ctrl+Shift+Z`。IME 変換中は無効
- Undo 実行も差分保存を通す

### 4-2. 保存の非同期化（課題 C3）

- 保存を UI スレッドから外し、書き込み用のスレッドかタスクに投げる
- 保存中も D&D を続けられるようにし、保存の完了・失敗だけを UI に返す
- 失敗時のロールバック方針は現状（メモリ上の状態を戻してエラー表示）を維持する

### 4-3. 複数ボード（課題 C4）

- サイドバーでボードを切り替える
- ボードの追加・名前変更・削除
- 最後に開いていたボードを記憶する（`app_state` テーブルか設定ファイル）

### 4-4. キーボード操作

- カード間の移動（矢印キー）、選択カードの編集（Enter）、削除（Delete）
- 選択カードのカラム間移動（`Ctrl` + 矢印キー）
- すべて IME 変換中は無効にする

### 4-5. エラー表示の改善（課題 C5）

- `format_move_error` / `format_card_error` の文字列整形をやめ、エラー種別に応じた UI（トースト、フィールド脇の注記）に振り分ける
- SQLite のエラーは原因が分かる形で出す
