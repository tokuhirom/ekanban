### 引き継ぐ設計の決まりごと

完了済みフェーズで決めたもののうち、今後の実装が従うもの。

- **期限は日付のみ**、`TEXT` の `'YYYY-MM-DD'` で持つ。時刻は持たない。必要になった時点で `due_time` を足す
- **絞り込みはカードを隠さず減光する。** 隠すとドロップの挿入位置が曖昧になり、D&D の意味が変わるため
- **並べ替えは一時的なビューではなく `position` の書き換え**として行う。見た目の位置と本来の位置が食い違わないようにする
- **履歴に残すのはカードのライフサイクルだけ**（`created` / `moved` / `archived` / `restored` / `deleted`）。カラム内の並べ替えと属性変更は残さない。既存データを遡って生成しない
- **Undo のスタックと `card_events` は共有しない。** 寿命（セッション / 永続）と目的（取り消し / フローの記録）が違う
- 保存はボード本体と履歴を 1 トランザクションで行い、失敗したらメモリ上の状態と `pending_events` の両方を捨てる
- 色だけに意味を持たせない。アイコンか文言で必ず区別できるようにする
- 入力欄・検索欄にフォーカスがある間はボードのショートカットを無効にし、IME とテキスト編集を優先する

### 既知の課題

C1〜C5（メモリ上の `max(id) + 1` 採番、全削除・再挿入の保存、UI スレッド上の同期保存、先頭ボードしか読まない `load_board`、エラーの文字列整形）はいずれも解消済み。

実使用で見つかった残りは GitHub issues にあり、フェーズ 8 で扱う（後述の「棚卸し（2026-09-05）」）。

## 精査（2026-09-04）: macOS のタスク管理アプリとして足りているか

機能の数では足りている。カード・カラム・期限・タグ・検索・アーカイブ・Undo・複数ボード・メニューバー・`.app` バンドルまで揃っており、README の方針に対する取りこぼしはない。

足りていないのは **毎日使ったときに最初にぶつかる箇所** で、いずれも機能の追加ではなく既存画面の是正になる。フェーズ 5 はこれを実装する。

| 見つかったこと | 根拠 | 影響 |
| --- | --- | --- |
| カラム内が縦にスクロールしない | `render_column`（`src/views/board.rs:2149`）に高さ制約も `overflow_y` もなく、ボードは `overflow_x_scroll` だけ | カードが十数枚を超えると下のカードが画面外に出て、選択も D&D もできなくなる。常用の障害としては最大 |
| カードを追加できるのが先頭カラムだけ | `add_card`（`src/views/board.rs:902`）が `columns.first()` 固定 | 「Doing に直接足す」ができず、追加のたびに D&D が要る |
| ウィンドウの大きさと位置が復元されない | `src/lib.rs:68` が毎回 1200x800 の中央固定 | macOS アプリとしての作法から外れる。`app_state` があるので保存先はある |
| 配色がダーク固定 | `src/views/board.rs` に `rgb(0x…)` が 45 箇所。gpui-kit の `Theme::sync_system_appearance` / `ActiveTheme::theme()` を使っていない | ライトモードの macOS で画面だけが黒く浮く。フェーズ 2-4 で決めた「テーマ色に対応づける」も未達 |
| `Ctrl+←/→` が macOS の Mission Control と衝突する | `handle_board_key_down`（`src/views/board.rs:815`）が `modifiers.control` を見ている | macOS 既定ではデスクトップ切り替えに取られ、カードが動かない |
| データの持ち出し手段がない | `src/db/` に export 相当がない | 「クラウド同期しない」方針の裏返しとして、壊れたときの回復手段がユーザーの手元にない。フェーズ 7 |

`card_events` の可視化（滞留・サイクルタイム・CFD）は 3.5 の判断どおり、データが貯まるまで保留のままとする。

## フェーズ 5: 常用に耐えるボード表示

### 5-0. 設計判断

**このフェーズは新しい概念を 1 つも足さない。** すべて既存画面の是正で、データモデルの変更は 5-3 と 5-6 の `app_state` の行が増えるだけとする。スキーマのバージョンは上げない。

### 5-1. カラム内の縦スクロール

- カラムのカード領域を、ヘッダとフッタを除いた残りの高さに収め、`overflow_y_scroll` を付ける
- カラムの高さはボードの高さに追従させる（カードの枚数で伸ばさない）
- 末尾の「ここにドロップ」のプレースホルダはスクロール領域の内側に置く。スクロールしないと落とせない位置にしない
- ドラッグ中、スクロール領域の上端・下端付近にカーソルが来たら自動でスクロールする。横方向（ボードの `overflow_x_scroll`）も同じ扱いにする
- キーボード選択（矢印キー）で画面外のカードに移ったとき、そのカードが見える位置までスクロールする

受け入れ条件:

- 1 カラムに 50 枚のカードを入れても、すべてのカードにスクロールで到達できる
- カラムのヘッダ（枚数表示・並べ替え・アーカイブ・編集・削除）はスクロールしても常に見える
- 50 枚のカラムの一番下のカードを、別カラムの一番上へ D&D で移せる
- 矢印キーで下に辿っていくと、選択中のカードが常に画面内にある

### 5-2. カラムごとのカード追加

- 各カラムのカード領域の末尾に「+ カードを追加」を置き、そのカラムの末尾にカードを作って編集を開く
- メニューとショートカット（`Cmd+N`）は、選択中のカードがあればそのカラム、なければ先頭カラムに追加する
- WIP 上限を超えても追加は禁止しない（3-3 と同じく警告に留める）

受け入れ条件:

- 3 番目のカラムの「+ カードを追加」で、そのカラムの末尾にカードが増える
- 追加直後にカード編集が開き、`Escape` で閉じてもカードは残る（既存の追加と同じ挙動）
- 追加が 1 回の保存で永続化され、Undo で取り消せる

### 5-3. ウィンドウの大きさと位置を復元する

- 終了時のウィンドウ矩形を `app_state` に保存し、次回起動時に復元する（`last_board_id` と同じ仕組みに相乗りする）
- 保存された矩形が現在のディスプレイ構成に収まらない場合は、既定の 1200x800 中央に戻す（外部ディスプレイを外したときに画面外で開かないため）
- フルスクリーン状態は保存しない。復元すると終了時の状態から抜けられなくなる事故が起きるため

受け入れ条件:

- ウィンドウを動かしてリサイズし、終了して起動し直すと同じ位置・大きさで開く
- `app_state` に矩形が無い（初回起動の）とき、従来どおり中央に 1200x800 で開く
- 画面外の座標が保存されていても、画面内に開く

### 5-4. 配色をテーマに載せ替える

`src/views/board.rs` の `rgb(0x…)` 直書き 45 箇所をやめ、gpui-kit のテーマ色に対応づける。

- 起動時とウィンドウの外観変更時に `Theme::sync_system_appearance` を呼び、システムのライト / ダークに追従する
- あわせて `Theme::sync_scrollbar_appearance` を呼び、スクロールバーの表示挙動を OS 設定に合わせる（5-1 でスクロールが増えるため）
- 色は `ActiveTheme::theme()` 経由で引く。対応づけは `background` / `card` / `border` / `foreground` / `muted_foreground` を基本とし、意味を持つ色は期限バッジの既存方針（`Overdue` は danger、`Today` は warning、`Soon` は accent、`Upcoming` は muted）に揃える
- WIP 超過のヘッダは danger、ドラッグ中の強調は accent を使う
- 表示メニューにライト / ダーク / システムに合わせるの切り替えを置き、選択を `app_state` に保存する

受け入れ条件:

- macOS の外観をライトに切り替えると、アプリ内の背景と文字色も追従する
- ダークのときの見た目が、現在の配色から大きく外れない
- `rg 'rgb\(0x' src/views/` がタグの色（ユーザーが指定した値）以外にヒットしない
- 期限バッジ・WIP 警告・ドラッグ中の強調が、ライトとダークの両方で判別できる

### 5-5. カード移動ショートカットを macOS と衝突しない組み合わせにする

- 選択カードのカラム間移動を `Ctrl+←/→` から `Cmd+Option+←/→` に変える。macOS の既定では `Ctrl+←/→` がデスクトップ切り替えに取られている
- あわせてカラム内での上下移動（`Cmd+Option+↑/↓`）も入れる。左右だけだと、移動先カラムの中での位置をキーボードだけでは決められない
- 変更後の割り当てを README のショートカット表に載せる（表そのものが無ければ作る）

受け入れ条件:

- macOS の既定設定のまま、選択カードが左右のカラムへ移動する
- 移動が既存のモデル移動処理を通り、保存と Undo と `card_events` の対象になる
- 入力欄・検索欄にフォーカスがある間は反応しない

### 5-6. フィルター状態の復元

前提だった `app_state` はフェーズ 4-3 で入ったので、ここで実施する。

- 検索語・タグ絞り込み・期限フィルターを `app_state` に保存し、起動時に復元する
- アーカイブ表示は復元しない。ボードではない画面で起動すると混乱するため
- 絞り込みが効いた状態で起動したときは、ヘッダの絞り込み表示を明示し、1 クリックで解除できるようにする

受け入れ条件:

- タグで絞り込んだまま終了して起動し直すと、同じ絞り込みが復元され、ヘッダにそれが見えている
- 絞り込みはカードを隠さず減光したままである（2-6 の方針を変えない）
- 保存されたタグが削除されていた場合、絞り込みなしで起動する

## フェーズ 6: カードの中身と操作性

> 旧フェーズ 5。番号だけを繰り下げたもので、内容と設計判断は変えていない。チェックリスト、コピー、コンテキストメニュー、カード番号表示まで実装済み。

### 6-0. 設計判断

**このフェーズの全項目は「新しい概念を増やさない」ことを条件に選んでいる。**

カードにはすでに、タイトル・説明・期限・タグ・アーカイブ状態があります。ここにフラグ、開始日、見積ポイントのような並列の属性を足すと、ユーザーは「どれをどう使い分けるか」を毎回考えることになります。このフェーズが足すのは、既存の概念の下に潜る 1 段（チェックリスト）と、既存の操作の近道（コピー・タグのトグル）だけです。

### 6-1. チェックリスト

カードを増やさずに粒度を下げる手段を用意します。「PR を出す」の下の「テストを書く」「fmt を通す」をカード化するとボードが埋まりますが、チェックリストなら埋まりません。

スキーマ v9:

```sql
CREATE TABLE checklist_items (
    id INTEGER PRIMARY KEY,
    card_id INTEGER NOT NULL,
    text TEXT NOT NULL,
    checked INTEGER NOT NULL DEFAULT 0,
    position INTEGER NOT NULL,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_checklist_items_card ON checklist_items(card_id, position);
ALTER TABLE boards ADD COLUMN next_checklist_item_id INTEGER NOT NULL DEFAULT 1;
```

ID 採番はフェーズ 0-1 と同じく単調増加とします。

**カード表面に出すのは進捗 1 行だけとする。**

```text
┌────────────────────┐
│ PR を出す            │
│ ■■■□□  3/5          │
│ ⚠ 今日 (09/04)      │
│ [bug] [ui]          │
└────────────────────┘
```

理由: チェックリストは、提案された機能の中で唯一 D&D に直接触ります。項目をカード表面に展開するとカード高さが項目数に比例し、ドラッグゴーストの大きさと挿入位置の判定がカードごとに大きく変わります。このアプリが最も重視しているのは D&D の直感性なので、**カード高さの増分は常に 1 行に固定します。**

- 項目が 0 件のカードには進捗行を出さない（期限バッジと同じ方針で、余白を増やさない）
- 項目の追加・チェック・並べ替え・削除はすべて `CardEditor` 内で行う
- `CardEditor` 内の項目の並べ替えはそこに閉じ、ボード上の D&D と混ざらないようにする
- 全項目をチェックしても、カードは自動でアーカイブも移動もしない。フローの状態変化は明示的な操作だけで起こす

受け入れ条件:

- 項目 0 件のカードで進捗行が出ない
- 項目を持つカードの表面の高さが、項目数によらず一定である
- カードを削除すると、その `checklist_items` も消える
- 期限あり・タグあり・チェックリストありのカードの round-trip テストが通る
- v8 の DB を開いて v9 になり、既存カードの項目が 0 件である

### 6-2. カードのコピー

- コンテキストメニュー（6-3）から、同じカラムの直下に複製する
- 引き継ぐもの: タイトル、説明、タグ、チェックリストの項目
- 引き継がないもの: 期限、チェック状態（すべて未チェックにリセットする）、アーカイブ状態
- 複製は `created` イベントを 1 件積む（フェーズ 3.5）

チェック状態をリセットするのは、コピーの主用途が「同じ手順をもう一度やる」だからです。

### 6-3. カードのコンテキストメニュー

タグの付け外しに `CardEditor` を開く必要をなくします。

- カードの右クリックでメニューを開き、タグをその場でトグルする
- 同じメニューに「コピー」「アーカイブ」「削除」を置く
- メニューを開く操作は、カード内の編集・削除ボタンと同じく、ドラッグ開始の対象から除外する

**フラグ（1 bit の重要マーク）は導入しない。** タグで代用でき、フラグが欲しくなる本当の理由は「タグの付け外しが重い」ことだからです。概念を増やさずに操作コストを下げれば同じ効果が得られます。

### 6-4. カード番号の表示

- `CardEditor` のヘッダに `#12` を出す
- **カード表面には出さない。** 期限バッジ・タグチップ・チェックリスト進捗ですでに情報量が多く、番号を見ても飛べない現状では割に合わないため
- URL スキームによるディープリンクは「前提が揃えば検討するもの」を参照

## フェーズ 7: データの持ち出しと復元（完了）

### 7-0. 設計判断

**クラウド同期を実装しないと決めている以上、手元にデータを取り出す手段は機能ではなく前提とみなす。**

SQLite ファイルは Time Machine のバックアップに入りますが、ユーザーがそれを知っているとは限らず、ファイルの場所（`~/Library/Application Support/ekanban/`）は Finder から辿りにくい場所にあります。「アカウントもサーバーも要らない」ことの引き換えに、壊れたときの回復がユーザーの手に負えないのでは方針が片肺になります。

**同期・インポートは作らない。** 取り込みを認めると ID の衝突と重複の解決が要り、それは実質的に同期の設計です。ここで用意するのは、読める形での書き出しと、ファイルそのもののコピーだけとします。

### 7-1. エクスポート

- ファイルメニューに「ボードを書き出す」を置き、保存ダイアログで出力先を選ばせる
- 形式は 2 つ
  - **JSON**: ボード・カラム・カード・タグ・チェックリスト・`card_events` をそのまま。将来インポートを作るならこれを入力にする
  - **Markdown**: カラムを見出し、カードを箇条書きにしたもの。人が読む・他のツールに貼る用
- 対象は現在のボードとする。全ボードの一括書き出しは、要望が出てから考える
- アーカイブ済みカードも含める（除外すると「消えた」ことになるため）

受け入れ条件:

- 期限・タグ・チェックリスト・アーカイブ済みカードを持つボードを JSON に書き出し、すべての項目が含まれている
- Markdown が、そのまま読んで内容が分かる
- 書き出し中も UI がブロックされない（フェーズ 4-2 の非同期保存と同じ扱いにする）
- 日本語がエスケープされずに UTF-8 で出る

### 7-2. バックアップ

- ヘルプメニューに「データベースをコピー…」を置き、SQLite ファイルを選んだ場所に複製する（`VACUUM INTO` を使い、保存中でも壊れない形で取る）
- あわせて「データの保存場所を Finder で開く」を置き、ファイルの場所を辿れるようにする

受け入れ条件:

- 保存キューに操作が残っている状態でコピーしても、コピー先が有効な SQLite ファイルとして開ける
- コピーしたファイルを `EKANBAN_DATABASE` に指定して起動すると、同じボードが表示される

## フェーズ 8: 実使用で出た当たりの調整

### 8-0. 設計判断

**このフェーズも新しい概念を 1 つも足さない。** フェーズ 5 と同じく、既に動いているものの当たりを直すだけにする。issue はどれも「機能が無い」ではなく「毎日見る画面がうるさい・読めない・戻せない」で、見た目と確認手順の問題として扱える。データモデルの変更は無く、スキーマのバージョンも上げない。

**操作の入口はコンテキストメニュー（6-3）に寄せる。** 6-3 で右クリックメニューを入れた時点で、カード表面とカラムヘッダに同じ操作のボタンを並べておく理由は無くなっている。二重に置いたまま片方を目立たなくするのではなく、常用しない操作はメニュー側に一本化する。

**確認ダイアログは Undo の代わりではない。** すべての削除に確認を出すと、読まずに押す確認になって役に立たなくなる。出すのは「Undo で戻せない」か「1 操作で複数件が消える」ものに限る。

### 8-1. 入力欄の配色を実機で確認して閉じる（#5）

- `render_board_editor` の `Input`（`src/views/board.rs:2190`）はフェーズ 5-4 以降テーマから色を引くため、issue #5 はテーマ対応前の症状とみられる。ライトとダークの両方で実機確認する
- 同じ確認を、カラム名編集・カード編集・タグ編集・検索欄にも通す。いずれも同じ `Input` を使っており、1 箇所が白いなら全部白い
- 直っていなければ、`Input` に渡す前景色・背景色をテーマ色として明示する

受け入れ条件:

- ライトとダークの両方で、すべての入力欄の入力文字が読める
- プレースホルダとエラー文言も、両方の外観で読める
- 日本語 IME の変換中の文字列も読める（共通の完了条件 6 と同じ確認）

### 8-2. カラムヘッダとカード表面のボタンを畳む（#3 / #6）

- カラムのタイトルを折り返さない（`whitespace_nowrap` と省略表示）。長い名前は末尾を省略する
- カラムヘッダに常時出すのは枚数表示（WIP を含む）だけにし、「期限順 / アーカイブ / 編集 / 削除」は `…` のオーバーフローメニューに畳む。これが #6 の直接の原因で、#3 の半分でもある
- カード表面の「編集 / アーカイブ / 削除」の常時表示をやめる。編集はカードのダブルクリック、残りは 6-3 のコンテキストメニューに任せる
- `danger`（赤）はダイアログの確定ボタンとメニュー内の削除項目だけに使い、一覧の上には置かない
- メニューバー（`src/menu.rs`）とショートカットの割り当ては変えない。畳むのは画面上のボタンだけ

受け入れ条件:

- カラム名が 1 行で表示され、1 文字ずつの折り返しが起きない。幅 280px のまま、名前が 10 文字でも崩れない
- カードにマウスを乗せていない状態のボードに、赤いボタンが 1 つも無い
- 期限順・アーカイブ・編集・削除がメニューから実行でき、挙動は畳む前と同じ（保存・Undo・`card_events` の扱いを変えない）
- メニューを開く操作が、6-3 と同じくドラッグ開始の対象から外れている

### 8-3. アプリアイコン（#7）

- 1024x1024 の元画像を 1 枚リポジトリに持ち、`iconutil` で `assets/icon.icns` を生成する手順を `Makefile` に入れる
- `script/bundle-mac` は `assets/icon.icns` があれば `CFBundleIconFile` を書く実装になっているので、置けば載る。スクリプト側の変更は不要
- Linux の `.desktop` とアイコンは、Linux のインストール手順を用意するときに合わせて考える。ここでは対象外とする

受け入れ条件:

- `.app` を作ると、Finder と Dock で専用のアイコンが出る
- 元画像と生成手順がリポジトリにあり、`.icns` を捨てても再生成できる
- 生成物（`.icns`）をコミットするかどうかを決めて、`.gitignore` と整合させる

### 8-4. 取り返しのつかない操作の確認をそろえる（#8）

- カラムの一括アーカイブ（`archive_column`、`src/views/board.rs:1458`）は、対象の枚数を示して確認する。1 操作で複数件が動くため
- カード 1 枚のアーカイブと削除には確認を出さない。Undo で戻せるうえ、最も回数の多い操作だから
- 空のカラムの削除は現状どおり確認しない（`request_delete_column` が既にそうしている）
- 確認して実行した操作も Undo の対象のままにする
- 文言は既存の 2 つ（ボード削除・カラム削除）に合わせ、「何が」「何件」消えるかを本文に書く

受け入れ条件:

- カードのあるカラムでアーカイブを実行すると、枚数入りの確認が出る
- 確認して実行したあと、Undo で元に戻せる
- カード 1 枚のアーカイブ・削除では確認が出ない
- 空のカラムの削除で確認が出ない

## スコープ外

## 検討して入れないと決めたもの

Trello と OmniFocus を参照して洗い出した候補のうち、検討のうえ実装しないと決めたものです。「思いつかなかった」のではなく「判断した」ことを残すために書いています。

| 項目 | 判断の理由 |
| --- | --- |
| 開始日（`defer_date`） | Kanban では「まだ着手しない」を**カラムが表している**。Backlog / Someday というカラムがあるのに日付でも同じことを表すと状態の表現が二重になり、「Ready カラムにあるが開始日が来ていないカード」が何を意味するのか答えられない。減光の条件がすでに 3 つ（検索・タグ・期限）あり、4 つ目を足すと「なぜこのカードが暗いのか」が読めなくなる。減光は D&D を壊さないための手段なので、それ自体が読めなくなっては本末転倒 |
| 保存されたビュー（Perspective） | ヘッダがすでに混んでいる（検索・タグ・期限・アーカイブ）。個人の 1 ボードでタグ数個・カラム数個の規模なら、絞り込みを手で作り直すコストはそもそも低い。OmniFocus の Perspective が効くのはプロジェクト数百のスケールがあってこそ |
| フラグ（1 bit の重要マーク） | タグで完全に代用できる。欲しくなる理由は操作コストなので、6-3 のコンテキストメニューで解決する |
| カードの複数選択 | 主用途である「Done をまとめて片付ける」は `archive_column` ですでに満たされている。複数選択の D&D はゴーストの見せ方と挿入枚数の表現が難しく、最重視の D&D の直感性を落とすリスクが実利に見合わない |
| カラムの折りたたみ | 折りたたんだ列への D&D の振る舞い（落とせないのか、ホバーで展開するのか、末尾固定で落とせるのか）がどれも今の一貫性から外れる。カラム 3〜5 個の現状では横スクロールに困っておらず、困っていない問題への対処になる |
| 見積ポイントと WIP のポイント制 | 個人ボードで見積の運用は続きにくく、空欄のまま放置されてポイント制が機能不全になる。枚数の粗さはむしろ「大きすぎるカードは分割しろ」という圧力として働く。加えてフェーズ 3.5 が入ったので**実測のサイクルタイム**が取れる。見積は実測の代替なので、実測が取れるなら要らない |
| グローバルホットキーのクイックキャプチャ | OS ごとの自前実装が必要で、macOS ではアクセシビリティ権限を要求することになる。「アカウント、サーバー、権限を必要としない」という方針と気分が合わない |
| 添付ファイル・カバー画像 | ローカル専用なので絶対パスを持つだけで実装できるが、ファイルが移動・削除されたときの破綻の面倒を見る価値がこのアプリにはない |
| カレンダー / タイムラインビュー | D&D の落とし先がボードとカレンダーで二重になり、最優先の方針と正面から衝突する |
| コメント欄・アクティビティフィード | 単独ユーザーでは薄い。「いつ何が起きたか」はフェーズ 3.5 の `card_events` が持つ |
| メニューバー常駐（ステータスバーアプリ） | 常駐の価値はクイックキャプチャと通知にあるが、前者は上記のとおり見送り、後者はスコープ外。残るのは「ウィンドウを速く出す」だけで、Dock と `Cmd+Tab` で足りている |

## 前提が揃えば検討するもの

現時点では実装しませんが、前提が満たされたら再検討する価値があるものです。

| 項目 | 前提 | 状況 |
| --- | --- | --- |
| 繰り返しカード | **明示的な「完了」の概念**。ekanban には今それがなく、Done カラムは慣習にすぎない。何を引き金に次を生成するかを定義できない。加えてバックグラウンド動作がないため、1 ヶ月起動しなければ日次カードが 30 枚生まれる。抑制の設計も要る | 未充足 |
| URL スキーム（`ekanban://board/1/card/12`） | **複数ボード**（形が決まらないと後で URL を壊す）。加えて登録方法が OS ごとに違い（macOS は `Info.plist`、Linux は `.desktop`、Windows はレジストリ）、既に起動中のアプリに URL を渡す単一インスタンス制御も要る | 複数ボードはフェーズ 4-3 で充足。残るのは単一インスタンス制御。カード番号の表示（6-4）が入って「番号を見たが飛べない」不満が実際に出たら着手する |
| 履歴の可視化（滞留・サイクルタイム・CFD） | **フェーズ 3.5 のデータが十分に貯まること**。何を見たいかはデータを見てから決める | 記録は開始済み。判断はデータ待ち |

## 各フェーズ共通の完了条件

1. `cargo fmt --all -- --check` が通る
2. `cargo clippy --all-targets --all-features -- -D warnings` が通る
3. `cargo test --all-features` が通る
4. モデルの変更には `#[cfg(test)]` のユニットテストが付いている
5. スキーマの変更には、旧バージョンの DB を開くマイグレーションテストが付いている
6. 入力欄を追加・変更した場合は、日本語 IME での入力を実機で確認している
7. README の「実装状況と次の実装」を更新している
