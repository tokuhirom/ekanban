## フェーズ 0: 基盤の是正

### 0-1. ID 採番を単調増加にする（課題 C1）

ボードごとに次の ID を保持し、削除では減らさない方式に変える。

- スキーマ v2 で `boards` に `next_card_id INTEGER NOT NULL DEFAULT 1` と `next_column_id INTEGER NOT NULL DEFAULT 1` を追加する
- 既存 DB のマイグレーション時に `MAX(id) + 1` で初期化する
- `Board` に `next_card_id` / `next_column_id` フィールドを持たせ、`add_card` / `add_column` はそこから採番して加算する

受け入れ条件:

- 「カードを 3 枚追加 → 3 枚目を削除 → 1 枚追加」で新しいカードの ID が 4 になるテストが通る
- 既存の `ekanban.sqlite3` を開いても ID が衝突しない

### 0-2. 保存を差分更新にする（課題 C2）

`save_board` の全削除・全挿入をやめる。

- `columns` / `cards` を `INSERT ... ON CONFLICT(id) DO UPDATE` で UPSERT する
- ボードに存在しない行だけを `DELETE FROM cards WHERE column_id IN (...) AND id NOT IN (...)` で消す
- 1 トランザクションで行う点は現状どおり維持する

受け入れ条件:

- 既存の round-trip テストがすべて通る
- 「カードを 1 枚移動して保存 → 別プロセスで読み直す」で `created_at` が保存前後で変わらないテストが通る（全削除・再挿入だと壊れやすい不変条件のため）

## フェーズ 2: 期限管理

### 2-0. 設計判断

**粒度は日付のみとする。** 時刻は持たない。

理由: Kanban のカードは「その日中にやる」単位で扱われることがほとんどで、時刻を持つとタイムゾーン変換・夏時間・「23:59 は今日か明日か」といった問題を、得られる価値に見合わないコストで抱え込むため。時刻付きリマインダーが必要になった時点で `due_time` を追加する後方互換な拡張余地は残る。

**保存形式は `TEXT` の `'YYYY-MM-DD'`。**

理由:

- 辞書順がそのまま日付順になるので `ORDER BY due_date` が素直に書ける
- `sqlite3` CLI で中身を直接読める
- タイムゾーンに依存しない絶対的な暦日として解釈できる
- `NULL` が「期限なし」を自然に表す

**依存の追加**: 「今日」をローカルタイムゾーンで求めるには std だけでは足りないため、`chrono`（0.4 系, `features = ["clock"]`）を追加する。日付の解析・整形・加算にも使う。追加時点の最新バージョンを確認すること。

### 2-1. スキーマ v3

```sql
ALTER TABLE cards ADD COLUMN due_date TEXT;
CREATE INDEX IF NOT EXISTS idx_cards_due_date ON cards(due_date);
```

- 既存行は `NULL`（期限なし）になり、後方互換
- `migrate()` のバージョン分岐に v3 を足す。v1 → v3 の一括適用と、v2 → v3 の差分適用の両方が通ること

### 2-2. モデル

```rust
// model.rs
pub struct Card {
    // ...
    pub due_date: Option<NaiveDate>,
}

impl Board {
    /// 期限を設定する。None で解除。変更がなければ false を返す。
    pub fn set_card_due_date(
        &mut self,
        card_id: CardId,
        due_date: Option<NaiveDate>,
    ) -> Result<bool, BoardError>;
}
```

- `add_card` は `due_date: None` で作る
- `update_card` のシグネチャは変えず、期限は別メソッドにする（編集ダイアログからは両方を呼ぶ）
- 不正な日付文字列は `BoardError::InvalidDueDate(String)` で弾く

### 2-3. 期限状態の判定

表示ロジックを純関数に切り出し、「今日」を引数で受け取る。テストで固定日付を渡せるようにするため、内部で現在時刻を読まないこと。

```rust
// model.rs
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum DueStatus {
    /// 期限切れ。超過日数を持つ。
    Overdue(i64),
    /// 今日が期限。
    Today,
    /// 期限が近い（残り 1〜3 日）。残日数を持つ。
    Soon(i64),
    /// それより先。
    Upcoming(i64),
    /// 期限なし。
    None,
}

pub fn due_status(due_date: Option<NaiveDate>, today: NaiveDate) -> DueStatus;
```

`Soon` の閾値 3 日は定数 `SOON_THRESHOLD_DAYS` として切り出し、後で設定可能にできるようにしておく。

### 2-4. カード上の表示

- カードのタイトル下に期限バッジを出す。期限が `None` のカードにはバッジを出さない（余白を増やさない）
- 表示文言は相対表現を優先し、絶対日付を併記する
  - `Overdue(n)` → 「n 日超過 (10/02)」
  - `Today` → 「今日 (10/05)」
  - `Soon(n)` → 「あと n 日 (10/07)」
  - `Upcoming(_)` → 「10/20」（同一年なら年を省略し、年をまたぐ場合のみ「2027/01/10」）
- 色は gpui-kit のテーマ色に対応づける。`Overdue` は danger、`Today` は warning、`Soon` は accent、`Upcoming` は muted
- 色だけに意味を持たせない。アイコンか文言で必ず区別できるようにする

### 2-5. 期限の編集 UI

既存の `CardEditor` に期限フィールドを足す。

- `YYYY-MM-DD` のテキスト入力（半角数字のみ、IME を通さない）
- クイック設定ボタン: 「今日」「明日」「今週末」「来週」「クリア」
- 不正な文字列はフィールド下に赤字でエラーを出し、保存ボタンを無効化する
- カレンダーピッカーはフェーズ 3 以降に回す。テキスト＋クイックボタンで実用に足りるため

### 2-6. 期限による並べ替えと絞り込み

**並べ替えは、一時的なビューではなく position を書き換える一回きりの操作にする。** カラムメニューの「期限順に並べ替える」を押すとカードの `position` を実際に書き換え、そのまま保存する。

理由: 並び順を一時的に差し替えると、ドラッグ＆ドロップの落とし先が「見た目の位置」なのか「本来の position」なのか曖昧になり、このアプリが最重視する D&D の直感性が壊れるため。

- 並べ替えキーは `(due_date が None は末尾, due_date 昇順, position 昇順)`
- 実行は Undo 対象にしたい（フェーズ 4 まではモデル上のロールバックのみ）

**絞り込み（「期限切れのみ」「今週まで」）は、カードを隠さず、非該当カードを減光して表示する。**

理由: カードを隠すと、隠れたカードをまたぐドロップの挿入位置が曖昧になるため。減光なら D&D の意味が変わらない。

### 2-7. テスト

- `due_status` の境界: 前日 / 当日 / 翌日 / 3 日後 / 4 日後、および `None`
- 年またぎ（12/31 と 1/1）と閏日（2/29）
- `set_card_due_date` が変更なしのとき `false` を返す
- DB の round-trip: 期限あり・期限なしの両方のカードを保存して読み直す
- マイグレーション: v1 の DB を開いて v3 になり、既存カードの `due_date` が `NULL` になる
- 日付文字列のパース失敗が `InvalidDueDate` になる

## フェーズ 3.5: 履歴の記録

### 3.5-0. 設計判断

**このフェーズを他より先に置く理由は、価値の大きさではなく、後から取り返せないことにある。**

他の機能はいつ実装しても同じものが手に入りますが、履歴だけは記録を始めた時点より前のデータが永久に欠けます。Kanban の中心的な指標（サイクルタイム、リードタイム、カード滞留、CFD）は、すべてカードがいつどのカラムに入ったかの記録から導かれます。`cards.updated_at` は上書きされるため履歴になりません。

**記録するのはカードのライフサイクルだけとする。**

| kind | 意味 | `from_column_id` | `to_column_id` |
| --- | --- | --- | --- |
| `created` | カードを作った | `NULL` | 作成先 |
| `moved` | 別のカラムへ移した | 移動元 | 移動先 |
| `archived` | アーカイブした | 直前のカラム | `NULL` |
| `restored` | アーカイブから戻した | `NULL` | 復元先 |
| `deleted` | 完全に削除した | 直前のカラム | `NULL` |

記録しないもの:

- **カラム内の並べ替え**（`from == to` の移動）。フローの状態は変わっておらず、D&D のたびにイベントが積み上がってノイズになるため
- **タイトル・説明・期限・タグの変更**。監査ログではなくフローの記録であり、これらを含めると肥大化に見合う読み手がいない

**Undo / Redo（4-1）の操作 enum とは共有しない。**

寿命と目的が違うためです。Undo はセッション内のメモリ上のスタックで、元に戻せる操作だけを持てばよい。履歴は永続で、Undo できない操作も残したい。共有すると「Undo のために持ちたくないもの」と「履歴に残したいもの」が衝突して、どちらかの設計が歪みます。イベントを書く場所（モデルの操作メソッド）が同じになるだけで十分です。

**削除されたカードのイベントも残す。**

`next_card_id` が単調増加で ID を再利用しないため、外部キー制約を張らなければ安全に残せます。「作って消した」という事実自体がフローの情報です。

**このフェーズでは読み出し UI を作らない。**

何を見たいかは、データが貯まってから決めます。確認は `sqlite3` CLI で直接行います。

### 3.5-1. スキーマ v7

```sql
CREATE TABLE card_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    board_id INTEGER NOT NULL,
    card_id INTEGER NOT NULL,
    kind TEXT NOT NULL,
    from_column_id INTEGER,
    to_column_id INTEGER,
    at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_card_events_card ON card_events(card_id, at);
CREATE INDEX IF NOT EXISTS idx_card_events_board ON card_events(board_id, at);
```

- `card_id` に外部キーを張らない（削除後もイベントを残すため）
- `id` はカード・カラムと違い、ボードごとの採番にしない。ユーザーに見えず、ボードをまたいだ時系列として読むため
- **既存データを遡って生成しない。** 記録開始より前のカラム遷移は復元できず、`created_at` から不正確な `created` イベントを合成すると、あとで実データと区別できなくなる。記録開始時刻は `schema_migrations` の v7 の `applied_at` がそのまま示すので、専用の列は要らない

### 3.5-2. モデル

```rust
// model.rs
pub struct CardEvent {
    pub card_id: CardId,
    pub kind: CardEventKind,
    pub from_column_id: Option<ColumnId>,
    pub to_column_id: Option<ColumnId>,
    pub at: i64,
}

pub struct Board {
    // ...
    /// 未保存のイベント。save_board が書き出して空にする。
    pending_events: Vec<CardEvent>,
}
```

- `add_card` / `move_card` / `archive_card` / `archive_column` / `restore_card` / `delete_card` がイベントを積む
- `archive_column` は対象カード 1 枚ごとにイベントを 1 件積む
- 保存はボード本体と同じ 1 トランザクションで行う
- **保存に失敗したら、メモリ上の状態をロールバックすると同時に `pending_events` も破棄する。** 起きなかった操作のイベントが次回の保存で書かれてはならない

### 3.5-3. 受け入れ条件

- カードを作り、別カラムに移し、アーカイブすると、`created` → `moved` → `archived` が時系列で残る
- カラム内で並べ替えてもイベントが増えない
- カードを完全に削除しても、そのカードのイベントは残る
- `archive_column` で 3 枚アーカイブすると `archived` が 3 件残る
- 保存に失敗したとき、`pending_events` が破棄され、次の保存で混ざらない
- v6 の DB を開いて v7 になり、既存カードのイベントが 0 件である
- v1 の DB を開いて v7 まで一括で上がる

## フェーズ 4: 運用性

### 4-1. Undo / Redo

- ボードのスナップショットではなく、操作を表す enum（`MoveCard`, `EditCard`, `SetDueDate`, ...）のスタックとして持つ
- `Ctrl+Z` / `Ctrl+Shift+Z`。IME 変換中は無効
- Undo 実行も差分保存を通す

### 4-2. 保存の非同期化（課題 C3）

- 保存を UI スレッドから外し、書き込み用のスレッドかタスクに投げる
- 保存中も D&D を続けられるようにし、保存の完了・失敗だけを UI に返す
- 失敗時のロールバック方針は現状（メモリ上の状態を戻してエラー表示）を維持する

### 4-3. 複数ボード（課題 C4）

- サイドバーでボードを切り替える
- ボードの追加・名前変更・削除
- 最後に開いていたボードを記憶する（`app_state` テーブルか設定ファイル）

### 4-4. キーボード操作

- カード間の移動（矢印キー）、選択カードの編集（Enter）、削除（Delete）
- 選択カードのカラム間移動（`Ctrl` + 矢印キー）
- すべて IME 変換中は無効にする

### 4-5. エラー表示の改善（課題 C5）

- `format_move_error` / `format_card_error` の文字列整形をやめ、エラー種別に応じた UI（トースト、フィールド脇の注記）に振り分ける
- SQLite のエラーは原因が分かる形で出す

## フェーズ 5: カードの中身と操作性

### 5-0. 設計判断

**このフェーズの全項目は「新しい概念を増やさない」ことを条件に選んでいる。**

カードにはすでに、タイトル・説明・期限・タグ・アーカイブ状態があります。ここにフラグ、開始日、見積ポイントのような並列の属性を足すと、ユーザーは「どれをどう使い分けるか」を毎回考えることになります。このフェーズが足すのは、既存の概念の下に潜る 1 段（チェックリスト）と、既存の操作の近道（コピー・タグのトグル）だけです。

### 5-1. チェックリスト

カードを増やさずに粒度を下げる手段を用意します。「PR を出す」の下の「テストを書く」「fmt を通す」をカード化するとボードが埋まりますが、チェックリストなら埋まりません。

スキーマ v8:

```sql
CREATE TABLE checklist_items (
    id INTEGER PRIMARY KEY,
    card_id INTEGER NOT NULL,
    text TEXT NOT NULL,
    checked INTEGER NOT NULL DEFAULT 0,
    position INTEGER NOT NULL,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_checklist_items_card ON checklist_items(card_id, position);
ALTER TABLE boards ADD COLUMN next_checklist_item_id INTEGER NOT NULL DEFAULT 1;
```

ID 採番はフェーズ 0-1 と同じく単調増加とします。

**カード表面に出すのは進捗 1 行だけとする。**

```text
┌────────────────────┐
│ PR を出す            │
│ ■■■□□  3/5          │
│ ⚠ 今日 (09/04)      │
│ [bug] [ui]          │
└────────────────────┘
```

理由: チェックリストは、提案された機能の中で唯一 D&D に直接触ります。項目をカード表面に展開するとカード高さが項目数に比例し、ドラッグゴーストの大きさと挿入位置の判定がカードごとに大きく変わります。このアプリが最も重視しているのは D&D の直感性なので、**カード高さの増分は常に 1 行に固定します。**

- 項目が 0 件のカードには進捗行を出さない（期限バッジと同じ方針で、余白を増やさない）
- 項目の追加・チェック・並べ替え・削除はすべて `CardEditor` 内で行う
- `CardEditor` 内の項目の並べ替えはそこに閉じ、ボード上の D&D と混ざらないようにする
- 全項目をチェックしても、カードは自動でアーカイブも移動もしない。フローの状態変化は明示的な操作だけで起こす

受け入れ条件:

- 項目 0 件のカードで進捗行が出ない
- 項目を持つカードの表面の高さが、項目数によらず一定である
- カードを削除すると、その `checklist_items` も消える
- 期限あり・タグあり・チェックリストありのカードの round-trip テストが通る
- v7 の DB を開いて v8 になり、既存カードの項目が 0 件である

### 5-2. カードのコピー

- コンテキストメニュー（5-3）から、同じカラムの直下に複製する
- 引き継ぐもの: タイトル、説明、タグ、チェックリストの項目
- 引き継がないもの: 期限、チェック状態（すべて未チェックにリセットする）、アーカイブ状態
- 複製は `created` イベントを 1 件積む（フェーズ 3.5）

チェック状態をリセットするのは、コピーの主用途が「同じ手順をもう一度やる」だからです。

### 5-3. カードのコンテキストメニュー

タグの付け外しに `CardEditor` を開く必要をなくします。

- カードの右クリックでメニューを開き、タグをその場でトグルする
- 同じメニューに「コピー」「アーカイブ」「削除」を置く
- メニューを開く操作は、カード内の編集・削除ボタンと同じく、ドラッグ開始の対象から除外する

**フラグ（1 bit の重要マーク）は導入しない。** タグで代用でき、フラグが欲しくなる本当の理由は「タグの付け外しが重い」ことだからです。概念を増やさずに操作コストを下げれば同じ効果が得られます。

### 5-4. カード番号の表示

- `CardEditor` のヘッダに `#12` を出す
- **カード表面には出さない。** 期限バッジ・タグチップ・チェックリスト進捗ですでに情報量が多く、番号を見ても飛べない現状では割に合わないため
- URL スキームによるディープリンクは「前提が揃えば検討するもの」を参照

## 検討して入れないと決めたもの

Trello と OmniFocus を参照して洗い出した候補のうち、検討のうえ実装しないと決めたものです。「思いつかなかった」のではなく「判断した」ことを残すために書いています。

| 項目 | 判断の理由 |
| --- | --- |
| 開始日（`defer_date`） | Kanban では「まだ着手しない」を**カラムが表している**。Backlog / Someday というカラムがあるのに日付でも同じことを表すと状態の表現が二重になり、「Ready カラムにあるが開始日が来ていないカード」が何を意味するのか答えられない。減光の条件がすでに 3 つ（検索・タグ・期限）あり、4 つ目を足すと「なぜこのカードが暗いのか」が読めなくなる。減光は D&D を壊さないための手段なので、それ自体が読めなくなっては本末転倒 |
| 保存されたビュー（Perspective） | ヘッダがすでに混んでいる（検索・タグ・期限・アーカイブ）。個人の 1 ボードでタグ数個・カラム数個の規模なら、絞り込みを手で作り直すコストはそもそも低い。OmniFocus の Perspective が効くのはプロジェクト数百のスケールがあってこそ |
| フラグ（1 bit の重要マーク） | タグで完全に代用できる。欲しくなる理由は操作コストなので、5-3 のコンテキストメニューで解決する |
| カードの複数選択 | 主用途である「Done をまとめて片付ける」は `archive_column` ですでに満たされている。複数選択の D&D はゴーストの見せ方と挿入枚数の表現が難しく、最重視の D&D の直感性を落とすリスクが実利に見合わない |
| カラムの折りたたみ | 折りたたんだ列への D&D の振る舞い（落とせないのか、ホバーで展開するのか、末尾固定で落とせるのか）がどれも今の一貫性から外れる。カラム 3〜5 個の現状では横スクロールに困っておらず、困っていない問題への対処になる |
| 見積ポイントと WIP のポイント制 | 個人ボードで見積の運用は続きにくく、空欄のまま放置されてポイント制が機能不全になる。枚数の粗さはむしろ「大きすぎるカードは分割しろ」という圧力として働く。加えてフェーズ 3.5 が入れば**実測のサイクルタイム**が取れる。見積は実測の代替なので、実測が取れるなら要らない |
| グローバルホットキーのクイックキャプチャ | OS ごとの自前実装が必要で、macOS ではアクセシビリティ権限を要求することになる。「アカウント、サーバー、権限を必要としない」という方針と気分が合わない |
| 添付ファイル・カバー画像 | ローカル専用なので絶対パスを持つだけで実装できるが、ファイルが移動・削除されたときの破綻の面倒を見る価値がこのアプリにはない |
| カレンダー / タイムラインビュー | D&D の落とし先がボードとカレンダーで二重になり、最優先の方針と正面から衝突する |
| コメント欄・アクティビティフィード | 単独ユーザーでは薄い。「いつ何が起きたか」はフェーズ 3.5 の `card_events` が持つ |

## 前提が揃えば検討するもの

現時点では実装しませんが、前提が満たされたら再検討する価値があるものです。

| 項目 | 前提 |
| --- | --- |
| 繰り返しカード | **明示的な「完了」の概念**。ekanban には今それがなく、Done カラムは慣習にすぎない。何を引き金に次を生成するかを定義できない。加えてバックグラウンド動作がないため、1 ヶ月起動しなければ日次カードが 30 枚生まれる。抑制の設計も要る |
| URL スキーム（`ekanban://...`） | **フェーズ 4-3 の複数ボード**。カード ID はボードごとの採番なので、複数ボードが入ると URL は `ekanban://board/1/card/12` の形になる。先に作ると URL 形式を後で壊す。加えて登録方法が OS ごとに違い（macOS は `Info.plist`、Linux は `.desktop`、Windows はレジストリ）、既に起動中のアプリに URL を渡す単一インスタンス制御も要る |
| フィルター状態の復元 | **フェーズ 4-3 の `app_state`**。「最後に開いていたボードを記憶する」と同じ仕組みに相乗りできる。ただし絞り込まれたまま起動して「カードが消えた」と誤解する事故を防ぐ表示が要る |
| 履歴の可視化（滞留・サイクルタイム・CFD） | **フェーズ 3.5 のデータが十分に貯まること**。何を見たいかはデータを見てから決める |
