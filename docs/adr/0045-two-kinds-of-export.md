# 0045. 書き出しは 2 つに分ける——Markdown は画面、JSON は置き場所

- 日付: 2026-09-08
- 状態: 有効
- 関連: [0039](0039-the-board-model-moves-to-typescript.md)、[0040](0040-the-shape-and-the-store-stay-in-rust.md)、[0035](0035-a-browser-build-of-the-real-core.md)

## 状況

[0039](0039-the-board-model-moves-to-typescript.md) の線引き——ウェブアプリとして作ったならサーバ側に書いただろうものだけを Rust に置く——を書き出しに当てると、最初は「両方とも webview」に見える。Markdown も JSON も、盤面という手元にあるデータを文字列にするだけだからである。

**JSON のほうを移そうとすると、移せないことが分かる。** 書き出す JSON には `board.next_card_id` / `next_column_id` / `next_tag_id` / `next_checklist_item_id` が入っている。この 4 つは `Board` の中で `#[serde(skip)]` になっていて、**webview には届かない**。届かないのは事故ではなく決めごとで、採番の続きは画面が知る必要のない値だからである。

つまり書き出しの 2 つは、同じ「盤面を文字列にする」ではなかった。

- **Markdown は、人が読むための表現**である。カラムの順に並べ、アーカイブを最後にまとめ、記号をエスケープする。材料は画面に出ているものだけで足りる
- **JSON は、置いてある形の写し**である。カードの履歴（`card_events`）も入る——これも置き場所しか持っていない

## 決定

**Markdown は webview（`web/src/model/export.ts`）、JSON は置き場所（`crates/core/src/export.rs`）。**

- 保存ダイアログに出す既定のファイル名（`suggestedExportName`）は webview。ボード名から作るもので、画面が持っている材料しか要らない
- 書き出しのコマンドは 2 つになる
  - `write_text_file(destination, extension, contents)` ——**中身は受け取るだけ**。拡張子が無ければ補い、書いたパスを返す
  - `export_board_json(destination)` ——組み立ても書き込みも置き場所の側
- ブラウザ版も同じ形で、書くところがダウンロードに変わるだけ（[ADR 0035](0035-a-browser-build-of-the-real-core.md)）

## 理由

**移せないものを、無理に移さないから。** JSON を webview に移すには、採番の続きを境界の向こうへ送るしかない。画面が使わない値を、書き出しのためだけに毎回のスナップショットへ載せることになる。[0039](0039-the-board-model-moves-to-typescript.md) が減らしたかったのは、まさにこの種の「境界を越えるためだけの荷物」である。

**線引きに当てても、同じ答えになるから。** ウェブアプリで「盤面を JSON で落とす」は、データベースを持っている側のエンドポイントとして書くのが自然である。一方「盤面を人が読める Markdown にして落とす」は、画面が持っているものだけで書ける。分かれ目は出力の形式ではなく、**材料が置き場所にしか無いかどうか**である。

**`write_text_file` が中身を見ないから。** 中身を組み立てるのが webview になっても、ファイルに書くのは殻の仕事のままである。パスの扱い（拡張子の補い）もそこに残る。この 1 本があれば、あとで別の形式が増えても置き場所の側は変わらない。

## 採らなかった案

- **JSON も webview で組み立て、`next_*` を書き出しから落とす。** 書き出しの形が変わる。読む相手がこちらの手元にいない以上、**フィールドを黙って減らすのは外から見える約束を変えること**で、行数のために払う値段ではない
- **JSON も webview で組み立て、採番の続きをスナップショットに載せる。** 画面が一度も読まない値を、盤面が変わるたびに往復させることになる
- **Markdown も置き場所に残す。** 材料は画面にあり、`crates/core` に残す理由が「いまそこにあるから」だけになる。エスケープと並べ方は表現の判断で、[0039](0039-the-board-model-moves-to-typescript.md) が webview に置くと決めたもの
- **`write_text_file` ではなく `export_board_markdown(destination)` にする。** 中身を組み立てるのが webview なのに、コマンドの名前が形式を知っていることになる。形式が増えるたびにコマンドが増える

## 結果

得るもの。

- 書き出しの分かれ目が、**材料がどちらにあるか**で説明できるようになる。形式ごとの好みではない
- Markdown の組み立て（エスケープ、空のカラムの文言、アーカイブの並べ方）が、それを読む人の近くに来る。テストも文字列そのものを見る形で webview 側に移った
- `write_text_file` は中身を見ないので、次に形式が増えても置き場所の側は変わらない

引き受ける不都合。

- **書き出しの経路が 2 本になる。** 「書き出す」という 1 つの操作に対して、通る道が形式で分かれる。`files.ts` がその分岐を持つ
- **JSON の中身は、これまでどおり Rust のテストと e2e でしか見られない。** webview 側の単体テストからは組み立てられない
