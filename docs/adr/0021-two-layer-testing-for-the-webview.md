# 0021. 画面のテストは、ハーネス経由の Playwright と、殻の煙テストに分ける

- 日付: 2026-09-06
- 状態: 有効
- 関連: #97、[0017](0017-moving-the-ui-to-tauri.md)

## 状況

[0017](0017-moving-the-ui-to-tauri.md) は、移る理由の 1 つに「テストが標準の道具に戻る」を挙げ、「webview なら Playwright がそのまま使える」と書いた。**設計に落とす段で、これが正確でないと分かった。**

Playwright が繋がるのは Chromium / Firefox / WebKit のビルドであって、アプリが埋め込む WKWebView・WebView2・WebKitGTK ではない。Tauri のアプリを外から動かす標準の道具は `tauri-driver`（WebDriver）で、これは Linux（WebKitWebDriver）と Windows（Edge WebDriver）でしか動かない。**macOS には WKWebView の WebDriver が無い。**

いま `src/views/board/view_tests.rs` の 1,047 行が、`TestPlatform` の上でウィンドウを開き、アクションとキー入力を流し、**画面の状態と SQLite に書かれた内容の両方**を見ている。この 1,047 行の行き先を決める必要がある。

## 決定

**4 層に分ける。画面の振る舞いの主役は、ハーネス経由の Playwright に置く。**

| 層 | 道具 | 担保するもの | 走る場所 |
| --- | --- | --- | --- |
| 中核 | `cargo test` | モデル・SQLite・スキーマ移行・バックアップ | 3 OS |
| **画面** | **Playwright ＋ `ekanban-harness`** | **操作から SQLite までを通した振る舞い。`view_tests.rs` の行き先** | Linux（CI）と手元 |
| 殻 | `tauri-driver`（WebdriverIO）の煙テスト | ウィンドウが開く・メニューが出る・キャプチャウィンドウが開く | Linux と Windows |
| 部品 | Vitest | 日付の表示、挿入位置の計算のような純粋な部分 | Linux（CI） |

`ekanban-harness` は、**`crates/core` を、Tauri のコマンドと同じ名前で HTTP に出すだけの開発用のバイナリ**である。webview はコマンドを `ipc/` の口を通して呼ぶので、口の実装を差し替えるだけで、同じ画面がふつうのブラウザでも動く。Playwright はそのブラウザを叩き、テストは一時ファイルの SQLite を直接読んで結果を確かめる。

macOS の殻は、手での確認に残す。

## 理由

**偽のバックエンドを書かないため。** ブラウザで動かすなら `invoke` を差し替えるのがふつうだが、TypeScript で書いた偽物は必ず本物からずれる。ずれた日、テストは通るのにアプリは壊れている。ハーネスなら**本物の `model.rs` と `db/mod.rs` が動く**ので、ずれようがない。

**いまのテストの形をそのまま移せるため。** `view_tests.rs` は「アクションを流して、画面と SQLite の両方を見る」形をしている。ハーネスは一時ファイルの SQLite を使うので、`Harness::stored_board` に当たるものがそのまま書ける。**移行で失うのは書き方であって、確かめている内容ではない。**

**`tauri-driver` だけに寄せられないため。** macOS で動かないので、それを主役にすると **3 つの OS のうち 1 つで画面のテストが 0 になる**。しかも WebDriver 経由は遅く、落ちたときに原因が webview なのかドライバなのかを切り分けにくい。数を絞った煙テストに向く道具で、1,000 行の受け皿には向かない。

**それでも殻の煙テストを残すのは、ハーネスでは触れないものがあるため。** ネイティブのメニュー、グローバルホットキー、2 つ目のウィンドウ、ファイルダイアログは、ブラウザの中には無い。

## 採らなかった案

- **Playwright を Tauri のアプリに直接繋ぐ。** 繋がらない。WKWebView にも WebView2 にも、Playwright の接続先が無い
- **`tauri-driver` に一本化する。** macOS が落ちる。実行も遅く、切り分けも難しい
- **`invoke` を TypeScript の偽物で差し替える。** 速いが、本物とずれる。ずれを防ぐために偽物を本物に追従させ続ける仕事が増える。それは 2 つ目の実装を持つのと変わらない
- **画面のテストを諦め、`cargo test` だけにする。** 移る理由の 1 つを捨てることになる。`render` の配線（アクションの付け忘れ、フォーカス中の抑止）が抜けても気づけない、といういまの問題がそのまま残る

## 結果

得るもの。画面の振る舞いを、本物のモデルと本物の SQLite に対して、標準の道具で書ける。実行は速く、落ちたときの原因が読み取れる。`view_tests.rs` が確かめていた内容が失われない。

引き受ける不都合。

- **開発用のバイナリを 1 つ持つことになる。** 薄く保つ（コマンドの定義は Tauri 側と共有し、違うのは運び方だけ）ことを条件にする。厚くなったら、それは 2 つ目のアプリである
- **ブラウザと webview の差は、この層では担保できない。** 殻の煙テストと、リリース前の手での確認に残る
- macOS の殻の確認が手作業のまま残る
- 待ち合わせの書き方が変わる。`run_until_parked()` は Playwright の待ち合わせ（要素の出現）になる。**実時間の `sleep` を書かない**という規則の意図はそのまま残る
