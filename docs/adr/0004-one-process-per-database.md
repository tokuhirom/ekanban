# 0004. 1 つのデータベースを開けるのは 1 プロセスだけにする

- 日付: 2026-09-05
- 状態: 有効
- 関連: [#61](https://github.com/tokuhirom/ekanban/issues/61) [#67](https://github.com/tokuhirom/ekanban/pull/67)

## 状況

単一インスタンスの制御が無く、ekanban は何個でも起動できた。2 つ起動すると、両方が同じ SQLite ファイルを開いたまま、それぞれ自分のボードをメモリに持つ。

保存は差分の UPSERT のあとに `DELETE ... WHERE board_id = ?1 AND id NOT IN (...)` で「自分の知らない行」を消す。そのため**あとから保存したほうが、もう片方で足したカードやカラムを消す**。しかも画面はどちらも自分の状態を出し続けるので、消えたことに気づけない。

Dock のアイコンを 2 回押す、ターミナルからも起動する、といった日常的な操作で踏める。

## 決定

起動時に、データベースの隣のロックファイル（`<データベース名>.lock`）へ排他ロックを取る。取れなければ**既に動いている**と判断し、理由を出して終了する。

ロックを取るのは**データベースを開くより前**。ロックのパスは**データベースのパスから作る**。

## 理由

- **開く前に取る理由。** 開いてからでは `migrate` と `seed_if_empty` が 2 つのプロセスから走る
- **PID ファイルではなくファイルロックにする理由。** PID ファイルは異常終了すると残り、次の起動を永久に塞ぐ。ファイルロックは OS がプロセスの終了時に落とす
- **データベース本体とは別ファイルにする理由。** SQLite のファイルそのものを掴むと、SQLite 自身のロックと混ざる
- **パス単位にする理由。** `EKANBAN_DATABASE` を使い分けて並べて動かす使い方（`docs/DEVELOPMENT.md` が勧めている）を潰さない

依存は増やしていない。`std::fs::File::try_lock` が Rust 1.89 で安定化されている。

## 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| **既存のウィンドウを前に出して 2 つ目は終了する**（issue が理想として挙げたもの） | 動いているプロセスに合図を送る経路（Unix ドメインソケット、D-Bus など OS ごとに違う仕組み）が要る。それは URL スキームの受け口と実質同じもので、`docs/DESIGN.md` が URL スキームを保留にしている理由そのもの。片方だけ先に作ると、あとで二重の仕組みになる |
| PID ファイル | 異常終了で残骸が残り、次の起動が永久に塞がれる |
| 保存の側で衝突を検出する | 検出できても「どちらを正とするか」を人に聞くことになり、マージの設計が要る。個人の 1 ファイルのアプリで持つには重い |
| 何もしない | 黙ってデータが消える。今日直したもののうち、再現条件が最も日常的だった |

## 結果

**良くなったこと。** 同じデータベースに対して 2 つ目は起動しない。2 つ目は理由をダイアログ（GUI 起動）か stderr（ターミナル）に出してから終了するので、黙って落ちない。

**引き受けた不都合。**

- **2 つ目の起動は「何も起きない」ように見えうる。** Dock から起動した場合、ダイアログが出るまでの短い間、反応が無いように見える
- 既存のウィンドウを前に出す動きはしない。使う人は自分でウィンドウを探すことになる。ここは URL スキームに着手するときにまとめて片付ける
- ロックファイルがデータディレクトリに 1 つ増える
