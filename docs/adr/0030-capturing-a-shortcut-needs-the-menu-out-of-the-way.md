# 0030. 割り当てを捕まえている間はメニューのアクセラレータを外し、押されているキーをその場に映す

- 日付: 2026-09-07
- 状態: 有効

## 状況

「クイックキャプチャのショートカット…」を開いて組み合わせを押しても、macOS では
**何も起きないように見えた**。

原因は 2 つある。

1 つめ。**メニューのアクセラレータが、webview より先に押されたキーを取る。** macOS の
`NSApplication` は、キーイベントをキーウィンドウに渡す前にメインメニューの
key equivalent を当てにいく。`menu.rs` が付けているのは `Cmd+N`（カードを追加）、
`Cmd+Shift+N`（カラムを追加）、`Cmd+Shift+B`、`Cmd+Shift+T`、`Cmd+S`、`Cmd+F`、
`Cmd+Shift+F`、`Cmd+Shift+A`、`Cmd+Ctrl+S` で、どれもクイックキャプチャに割り当てたく
なる組み合わせである。押すとメニューの項目が動き、`keydown` はダイアログまで届かない。
同じことは GTK のアクセラレータでも起きる。

2 つめ。**届かなかったことが画面から読めない。** ダイアログは最初の `keydown` で割り当てて
そのまま閉じる作りで、押されているキーも、登録された組み合わせも、どこにも出さない。
キーが届いていないのか、届いて断られたのか、届いて登録できたのかが区別できない。

これに、**保存されているのに登録できていない割り当ての扱い**が重なる。起動のときの登録に
失敗しても理由はログに落ちるだけで、設定は保存されたまま残る（`docs/DESIGN.md`
「クイックキャプチャ」がそう決めている）。画面には効いている割り当てとして出るので、
押しても開かない理由がやはり読めない。

## 決定

3 つを決める。

**割り当てを捕まえている間は、メニューがキーを取らない状態にする。** ダイアログが開いた
ときに `set_menu_accelerators_active(false)`、閉じるときに `true` を呼ぶ。外すのは
`menu.rs` の `sections()` が付けている自前の項目だけで、`Predefined` の項目（`Cmd+Q`、
`Cmd+W`、`Cmd+C` など OS のもの）はそのままにする。

外すには**アクセラレータを外すのと、項目を無効にするのと、両方を行う**。muda は
macOS でアクセラレータを外せない（`set_key_accelerator(None)` が `NSMenuItem` の
key equivalent に触らずに返る）ので、そこは無効な項目が key equivalent を実行しない
ことで止める。GTK と Windows はアクセラレータの側が実際に外れる。

付け直す形は控えを持ち回さず `sections()` から作り直す。アクセラレータも、押せるか
どうかも、そこから読む。

**押されているキーを、押している間そのまま映す。** 修飾キーだけを押している途中も映す。
割り当てたあともダイアログを閉じず、登録された組み合わせをその場に出す。

**保存されているのに登録できていない理由を残し、ダイアログに出す。** 起動のときの登録の
失敗を `capture::Registration` に置き、`quick_capture_status` が読む。新しい割り当ての
登録に失敗したときは、外した前の割り当てを登録し直す。

## 理由

メニューのアクセラレータを外すのは、**ほかに押されたキーを webview へ通す道がない**からで
ある。OS がアプリのメニューを先に見るのは仕様で、webview 側で先回りして止める手がない。
外している間は割り当てを捕まえるダイアログが開いているときだけなので、盤面の操作は
どのみち後ろにある。

外した控えを持ち回さず `sections()` から作り直すのは、**控えを取り損ねた経路が 1 つでも
あれば割り当てが消えたままになる**からである。組み立てたときと同じ関数から作れば、
戻した形が組み立てた形と食い違いようがない。

押されているキーを映すのは、**押しても何も起きないときに次に何をすればよいかが分かる**の
がここだけだからである。何も出なければキーが届いていない、出て断られれば理由が出る、
出て登録できれば組み合わせが残る。3 つが画面で区別できる。閉じないのも同じ理由で、
閉じてしまうと何が登録されたのかを読む間がない。

登録できていない理由を出すのは、`docs/DESIGN.md`「アプリが伝えること」の「使う人が手を
打たないと直らない失敗」にあたるからである。ほかのアプリがその組み合わせを握っている
なら、そちらを閉じるか、別の組み合わせに変えるしかない。理由が出なければどちらも
選べない。

## 採らなかった案

- **アクセラレータを外すだけにする。** macOS で効かない。muda の
  `set_key_accelerator(None)` は `NSMenuItem` に触らずに返るので、`Cmd+N` は
  メニューに取られたままになる。**直そうとしていた環境だけが直らない。**
- **項目を無効にするだけにする。** macOS では通るが、GTK と Windows では
  アクセラレータが残る。GTK は insensitive な項目でアクセラレータが発火しない
  ので実際には止まるが、Windows のアクセラレータテーブルは項目の状態と別に
  引かれる。3 つの環境それぞれで違う理由に頼ることになる。
- **メニューごと外して、閉じるときに組み直す。** macOS ではメニューバーが空になり、
  ダイアログが出ている間だけアプリが壊れて見える。組み直しは項目を作り直すことなので、
  外している間に押されたメニュー操作の行き先も変わる。
- **割り当てに使える組み合わせから、メニューが使っているものを除く。** 除いた組み合わせを
  なぜ選べないのか説明できない。しかも `Cmd+N` はクイックキャプチャに最も選ばれそうな
  組み合わせで、これを塞ぐのは機能を削るのに近い。
- **押されたキーを Rust 側で捕まえる。** グローバルホットキーの登録をキー 1 つずつ試す
  ことになり、試している間ほかのアプリからそのキーを奪う。
- **押されているキーを、確定のボタンを押すまで割り当てない。** 見えることと、1 回の
  打鍵で決まることは両立できる。ボタンを足すと、そのボタン自身に割り当てたいキー
  （`Enter`、`Space`）を押せなくなる。

## 結果

`Cmd+N` のような、メニューが使っている組み合わせもクイックキャプチャに割り当てられる
ようになった。割り当てている間はメニューのその割り当てが効かないが、割り当てたあとは
両方が並び立つ——メニューはアプリが前面にいるときだけ、グローバルホットキーはそれ以外の
ときに効く。

押しても何も起きない状態が画面から読めるようになった。キーが届いていない、断られた、
登録できていない、の 3 つがそれぞれ違う出かたをする。

引き受けた不都合は、**ダイアログが開いている間、自前のメニュー項目が灰色になり、
アクセラレータの表示も消える**ことである。ダイアログを閉じれば、組み立てたときと同じ
形に戻る。割り当てを決めている最中にメニューから盤面を触れないのは、そもそも困らない。
