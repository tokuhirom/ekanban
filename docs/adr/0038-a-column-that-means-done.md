# 0038. 「終わったもの」の置き場であることを、カラムの属性にする

- 日付: 2026-09-08
- 状態: 有効

## 状況

初回に作られるボードには「やること / 進行中 / 完了」の 3 カラムがあるが、
**「完了」はただの名前**で、アプリはそれが終わったものの置き場だと知らない。
名前を「Done」に変えても「済」に変えても、振る舞いは何も変わらない。

そのため、終わったカードが終わっていないカードと同じ濃さで並ぶ。とくに困るのが
期限で、先週やり終えたカードが「⚠ 9/1（7日超過）」と赤で出続ける。ボード一覧の
`⚠` の件数にも入るので、**やることが残っているように見えるのに、開くと全部
終わっている**。期限切れの赤が、片付いたカードの分だけ薄まる——
[ADR 0034](0034-dropping-the-wip-limit.md) が WIP 上限を消した理由と同じ形の劣化である。

アーカイブすればこの問題は消えるが、アーカイブは盤面から見えなくなる操作で、
「今週やったこと」を見えるところに残しておきたい期間とは目的が違う。盤面に
置いたまま、終わったものとして扱える必要がある。

**終わったものの置き場は 1 本とは限らない。** 「完了」の隣に「キャンセル済み」
（あるいは「却下」）を置く使い方は普通にあり、そこに入ったカードも同じように
静かであってほしい。

`docs/DESIGN.md`「前提が揃えば検討するもの」の繰り返しカードが挙げている前提
「**明示的な「完了」の概念**。ekanban には今それがなく、Done カラムは慣習にすぎない」
は、ここのことである。

## 決定

**カラムに「終わったものの置き場である」という 1 bit を持たせる。**
`Column.done: bool`（SQLite では `columns.done`、スキーマ移行 12）。

- **何本でも立てられる。** 「完了」と「キャンセル済み」の両方に立てられ、
  どちらも同じ扱いになる
- カラムの `…` メニューの「完了扱いにする」/「完了扱いをやめる」で切り替える。
  コマンドは `set_column_done(column_id, done)` の 1 つで、Undo も 1 手
- 立っているカラムのヘッダには `✓` の印を出す（読み上げ名「完了扱い」）
- **`done` のカラムにあるカードは、期限の件数（`⚠` `◷`）に数えない。**
  アーカイブ済みを数えないのと同じ理由——終わったものに期限切れも本日期限も無い
- 件数から 1 枚へ辿る導線（[ADR 0011](0011-due-counts-in-the-board-list.md) の `firstDueCard`）も
  同じ条件で飛ばす。数えていない場所へ着くと、押した数と着いた場所が食い違う
- **`done` のカラムのカードはトーンダウンして描く。** 期限は日付だけを `muted` で
  出し、`⚠` `◷` と「N日超過」「あとN日」を落とす。タイトル・説明・チェックリストも
  `--color-muted-foreground` にし、タグのチップは彩度を落とす
- **トーンダウンに `opacity` は使わない。** カード全体の `opacity` は絞り込みの減光が
  既に使っている。完了は**色**で、絞り込みは**濃さ**で表し、暗いカードの理由が
  1 つに読めるようにする（`docs/DESIGN.md`「絞り込みと検索」）
- 新しく作るボードには「やること」と「完了」の 2 カラムを置き、後者を `done` に
  する（`Board::new_empty`）。初回のボード（`Board::first_run`）の「完了」も同じ
- **既存のデータベースでは、移行で 1 本も立てない。** 名前からは推測しない

## 理由

**「終わった」は置き場が複数あり得る。** 完了とキャンセルは別の終わり方だが、
「もう手を動かさない」という点では同じで、期限が赤いままでは困るのも同じである。
ボード側に「完了カラムはこれ」という 1 つの指定を持たせる形だと、キャンセル済みを
作った時点で表せなくなる。カラムの属性にすれば、置き場が 2 本でも 3 本でも同じ
1 bit で足りる。

**完了とキャンセルを区別しない**のは、区別した結果として変わるものが今は無いから
である。見せ方も、期限の数え方も、盤面での置き場所も同じになる。違う扱いが要ると
分かった時点で、この 1 bit を種類に広げるほうが、先に 2 種類を作って片方を使わない
より安い。

**カラムの属性は Undo と相性がよい。** `BoardOperation::RemoveColumn` は消した
`Column` を丸ごと持っているので、消して戻せば `done` もそのまま戻る。ボード側に
ID を持たせる形だと、カラムを消したときに指定を消し、Undo のときに戻す処理を
別に書くことになる。

**期限の件数から外すことが、この機能の実体である。** トーンダウンは見た目の話だが、
件数は「開かなくても分かるようにする」ために出しているもの（[ADR 0011](0011-due-counts-in-the-board-list.md)）で、
終わったカードが入っていると出す意味が無くなる。ここを直さずに色だけ薄くすると、
盤面は静かなのに一覧は赤いという食い違いが残る。数えているのは SQL
（`load_boards_as_of`）と `Board::due_counts` と `StoredBoard::summary` の 3 か所なので、
3 か所とも同じ条件にする。

**`opacity` を使わない**のは、絞り込みの減光と混ざるからである。`docs/DESIGN.md` は
絞り込みの条件を 2 つに保つ理由として「なぜこのカードが暗いのか」が読めなくなる
ことを挙げている。同じ表現手段を 2 つ目の意味に使えば、条件を増やしたのと同じことになる。

**移行で名前から推測しない**のは、推測が当たったときの利得より外したときの害が
大きいからである。「完了」「Done」「済」「キャンセル」を並べても漏れるし、当たった
ボードでは黙って期限の件数が減る。**設定していないのに数字が変わる**のは、
[ADR 0028](0028-a-single-default-quick-capture-target.md) が「書き込んだ時点でユーザーが
選んだことになる」を避けたのと同じ筋で避ける。立てるのは 2 クリックで、印はヘッダに出る。

**新しいボードに「完了」を置く**のは、1 カラムのボードでは完了扱いという概念が
画面のどこにも出ないからである。`docs/DESIGN.md`「初回に見えるものに、消す前提の
ものを置かない」に触れないのは、置くのがカラムだけで、カードを 1 枚も入れないため
——初回シードが 3 カラムを置いているのと同じ判断である。

## 採らなかった案

- **ボードの属性にして 1 本だけ選ばせる（`boards.completed_column_id`）。**
  「多くても 1 本」をスキーマの形で持てるのは利点だが、キャンセル済みを同じ扱いに
  できない。1 本に絞る値打ちよりも、終わりの置き場を分けたい要求のほうが実際に起きる
- **`done` ではなく種類を持たせる（`ColumnKind::Done | Cancelled`）。** 名前は
  カラム名がすでに持っているので、種類は見せ方を変えるためだけのものになる。
  同じ見せ方をする 2 つの値は、区別ではなく重複である
- **カード側に完了フラグを持たせる。** Kanban ではカードの状態は**どのカラムに
  あるか**で表れている。フラグを足すと「完了カラムにあるが未完了のカード」が
  何を意味するのか答えられなくなる（`docs/DESIGN.md` が開始日を入れないと決めた
  理由と同じ）
- **完了扱いのカラムに入れたら自動でアーカイブする。** 盤面に「今週やったこと」を
  残すという、この機能の目的そのものを消す。アーカイブは今までどおりカラムの
  `…` の「アーカイブ」で明示的に行う
- **完了扱いのカラムのカードを盤面から隠す。** D&D の落とし先が消え、戻す操作が
  アーカイブ表示経由になる。減光ではなく非表示にするのはアーカイブ表示だけ、
  という [ADR 0010](0010-hiding-instead-of-dimming-in-the-archive.md) の線を越える
- **`card_events` に `completed` を足す。** 完了扱いのカラムへの移動は既に `moved` と
  して `to_column_id` つきで残っている。同じ事実を 2 つの形で持つと、あとで
  サイクルタイムを出すときにどちらが正かを決めることになる
- **期限そのものを、完了扱いのカラムでは消す。** 消すと戻したときに復元できない。
  出さないのは表示の判断に留め、データは触らない

## 結果

終わったカードが盤面で静かになり、ボード一覧の `⚠` が「まだ手が要るもの」の数に
なる。カラムの名前を何にしても（「Done」でも「済」でも「キャンセル済み」でも）
同じ扱いにできる。

`docs/DESIGN.md`「前提が揃えば検討するもの」の繰り返しカードは、前提のうち
**明示的な「完了」の概念**が満たされた。残る前提（バックグラウンド動作が無いため
1 ヶ月起動しなければ日次カードが 30 枚生まれることの抑制）は変わっていないので、
まだ実装しない。

引き受けた不都合は 3 つ。

- **既存のボードでは、自分で立てるまで何も変わらない。** 移行で推測しない判断の
  裏返しである
- **完了扱いのカラムに入れたまま放置したカードは、期限が来ても静かなままになる。**
  期限切れを知りたいなら、そのカードはそこに置くべきではない、ということでもある
- **全部のカラムに `done` を立てることもできる。** 盤面全体が静かになるだけで
  壊れはしないので、禁止しない。禁止すると「なぜ立てられないのか」を説明する
  必要が出る
