# 0020. D&D はポインタイベントで作り、HTML5 の drag events は使わない

- 日付: 2026-09-06
- 状態: 有効
- 関連: #97、[0017](0017-moving-the-ui-to-tauri.md)

## 状況

README が「いちばん大事にしています」と書いているのは D&D の手触りで、[0017](0017-moving-the-ui-to-tauri.md) は**移行の成否をここで判定する**と書いた。webview で同じ水準に届かなければ、移行そのものが失敗になる。

web で D&D を作る道は 3 つある。HTML5 の drag events、ポインタイベント（`pointerdown` / `pointermove` / `pointerup`）に載せた既製のライブラリ、そして自前のポインタ実装である。

いま gpui 側で成立している手触りは、`on_drag` のゴースト、`drag_over` の枠の強調、カラム端でのオートスクロール、`drag_over` 中も減光したカードに落とせること、カラムそのものの並べ替え、キーボードでのカード移動——の 6 つでできている。

## 決定

**ポインタイベントで作る。HTML5 の drag events は使わない。**

既製のライブラリ（dnd-kit）に載せるのを既定とし、段階 4 の spike で次の受け入れ条件を 3 つの webview（WKWebView / WebView2 / WebKitGTK）で確かめる。届かなければポインタイベントで自前に書く。**どちらにするかは spike の結果で決め、条件を下げて通さない。**

| # | 条件 |
| --- | --- |
| 1 | 掴んだカードのゴーストがポインタに遅れずついてくる |
| 2 | 落とす位置（どのカラムの何枚目か）が、落とす前に見て分かる |
| 3 | カラムの端にポインタを寄せると自動でスクロールし、押したまま端で止めても滑らかに続く |
| 4 | 減光しているカードの位置にも落とせる |
| 5 | カラムそのものの並べ替えも、カードと同じ操作感でできる |
| 6 | キーボードでもカードを動かせる |
| 7 | 落としてから画面が確定するまでに間が空かない |
| 8 | 3 つの webview で 1〜7 が同じ |

ドラッグ中は webview の中だけで完結させ、`drop` の 1 回だけ `move_card` / `move_column` を呼ぶ（[0018](0018-rust-owns-the-board-state.md)）。

## 理由

**HTML5 の drag events では条件 1・2・8 に届かないから。** ゴーストの描画がブラウザ（と OS）のもので、見た目も追従も制御できない。`dragover` の発火は間引かれ、挿入位置の更新が粗くなる。そして WebKitGTK と WKWebView と WebView2 で挙動が揃わない——**プラットフォーム差から逃げるための移行で、いちばん大事な部分にプラットフォーム差を持ち込む**ことになる。

**ポインタイベントなら、いまと同じものを同じ考え方で書けるから。** `setPointerCapture` で掴んだ先を固定でき、ゴーストは自分の要素なので見た目も追従も自分のもの。挿入位置の計算はいまの実装（カラムなら末尾の index、カードなら自分の index）がそのまま移る。

**既製のライブラリを既定にするのは、周辺が多いから。** ゴースト、挿入位置の可視化、オートスクロール、キーボード操作、複数の入力手段——条件 3 と 6 は特に、自分で書くと手触りの調整が延々と続く。[0017](0017-moving-the-ui-to-tauri.md) が「作りたいのは Kanban であって UI ツールキットではない」と書いた以上、ここも同じ基準で判断する。

**それでも spike を先に置くのは、ここだけは実測でしか分からないから。** 移行の成否がかかっているものを、「よく使われているから大丈夫だろう」で通さない。

## 採らなかった案

- **HTML5 の drag events。** 上記のとおり。webview 間で揃わないことが決定的
- **最初から自前で書く。** 条件 3 と 6 の作り込みに時間がかかり、そのぶん移行が遅れる。既製で足りるなら足りたほうがよく、足りないと分かってから書けばいい。退路として残す
- **D&D をやめてキーボードとメニューだけにする。** README の中心にあるものを捨てることになる。それは移行ではなく別のアプリ

## 結果

得るもの。手触りの責任が自分の側に残る。ブラウザごとの差に振り回されない。挿入位置の判定を、いまの実装からそのまま移せる。

引き受ける不都合。

- ライブラリを使う場合、その保守に乗ることになる。web の D&D ライブラリは移り変わりが速く、**gpui のフォーク乱立から逃げた先で、また 1 つ供給の不安を抱える**。抱えるのは 1 つだけにし、外しても自前に落とせる形（挿入位置の計算を自分の関数に保つ）で使う
- 条件 8 の確認には 3 つの OS が要る。CI では担保しきれず、手での確認が残る
- カード表面の高さを可変にしない規則（チェックリストの件数で高さを変えない）は、条件 2 の安定のために webview でも残る
