# 設計判断の記録（ADR）

1 つの判断につき 1 ファイル。**いつ・何を・何と迷って決めたか**を残します。

## [設計の記録](../DESIGN.md) との分担

2 つあるのは、読みたいものが違うからです。

| | 見るもの | 形 | 書き換え |
| --- | --- | --- | --- |
| [`docs/DESIGN.md`](../DESIGN.md) | **いま従うべき規則**。「新しいコードは何を守るのか」 | 短い箇条書き。常に現在形 | 判断が変われば**書き換える** |
| `docs/adr/` | **その規則になった経緯**。「なぜそうなったのか」「何を捨てたのか」 | 1 判断 1 ファイル。日付つき | **書き換えない**（下記） |

読む順は `docs/DESIGN.md` が先です。従うべきことはあちらに全部あります。ADR は、その 1 行に納得がいかないときや、覆すべきか考えるときに開くものです。

**同じ内容を両方に書きません。** `docs/DESIGN.md` は規則だけ、ADR は経緯だけ。経緯が要る規則には、`docs/DESIGN.md` 側から ADR へのリンクを付けます。

## いつ書くか

**判断のたびに書くものではありません。** 次のどれかに当てはまるときに書きます。

| | 例 |
| --- | --- |
| [`docs/DESIGN.md`](../DESIGN.md) の決まりごとを**足す・書き換える・破る** | 「常用しない操作を画面に常時出さない」に反する UI を、理由があって入れる |
| **判断を覆す** | [0001](0001-links-in-the-description.md) → [0002](0002-links-inside-the-description-field.md)。前の判断が ADR になっていなくても、覆すなら書く |
| 実在した**代替案**があり、選ばなかった理由に残す値打ちがある | `TitleBar` を使うか自前で書くか |
| **外から見える約束**を変える | データの置き場所や形式、キーの割り当て、プラットフォームごとの差 |
| **依存を足す・差し替える** | `lsp-types` を直接の依存にする |
| issue の受け入れ条件に**書かれていない判断**を、実装の都合で下した | 「起動ごと」と書かれていたものを「日ごと」にする |

**書かなくてよいもの。**

- バグ修正、文言の直し、リファクタリング
- issue に書かれた受け入れ条件を、書かれたとおりに満たす実装
- 一度きりで、あとから誰も理由を問わないもの

何にでも書く運用にすると、読まれなくなります。**迷ったら「半年後の自分がこの行を見て『なぜ？』と思うか」で決めます。** 思うなら書きます。

判断が要るのは実装の前です。[`implement-issue`](../../.claude/skills/implement-issue/SKILL.md) は、設計を issue にコメントする段階でここを見ます。

## 書き方

`NNNN-短い英語のスラッグ.md`。番号は連番で、欠番も再利用もしません。

```markdown
# NNNN. <決めたことを 1 行で>

- 日付: YYYY-MM-DD
- 状態: 有効 / 置き換えられた（→ NNNN）
- 関連: #<issue> #<PR>

## 状況

<何が起きていて、何を決める必要があったか>

## 決定

<決めたこと。命令形ではなく、決めた内容そのもの>

## 理由

<なぜそれを選んだか>

## 採らなかった案

<検討して選ばなかったもの。**なぜ選ばなかったか**まで書く>

## 結果

<この決定によって、良くなったことと、引き受けた不都合>
```

## 覆すとき

**既にある ADR を書き換えません。** 新しい ADR を足し、古いほうの「状態」に「置き換えられた（→ 新しい番号）」と書き足します。これだけが例外的な追記です。

書き換えてしまうと、「なぜ最初はそう決めたのか」が消えます。それが消えると、同じ理由で同じ判断に戻ってくることになります。実際に [0001](0001-links-in-the-description.md) がその形で置き換えられています。
