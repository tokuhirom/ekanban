# 0007. 重大な決定は ADR に残すことを、完了条件にする

- 日付: 2026-09-05
- 状態: 有効
- 関連: [#75](https://github.com/tokuhirom/ekanban/issues/75)、[#73](https://github.com/tokuhirom/ekanban/issues/73) [#74](https://github.com/tokuhirom/ekanban/pull/74) の続き

## 状況

[#73](https://github.com/tokuhirom/ekanban/issues/73) で `docs/adr/` を作り、書き方も [`docs/DESIGN.md`](../DESIGN.md) との分担も決めた。しかしそこにあったのは**そういう場所がある**という説明までで、「いつ書かなければならないか」が無かった。

そのままだと、書くかどうかがそのとき手を動かした人（かエージェント）の気分で決まる。書き忘れても何も落ちない。`docs/DESIGN.md` の決まりごとが、経緯を持たないまま増えていく元の状態に戻る。

`docs/DESIGN.md` には既に「変更の完了条件」があり、fmt / clippy / テスト / マイグレーションテスト / 実機確認が並んでいる。**このリポジトリで「必ずやること」を担保している仕組みはここ**だった。

## 決定

**重大な決定をしたら、その issue を閉じる前に ADR に残す。** 「変更の完了条件」の 10 番として入れる。

「重大」の判定は [`docs/adr/README.md` の「いつ書くか」](README.md#いつ書くか) に表として置く。要るのは次のとき。

- `docs/DESIGN.md` の決まりごとを足す・書き換える・破る
- 判断を覆す
- 実在した代替案があり、選ばなかった理由に残す値打ちがある
- 外から見える約束を変える（データの置き場所や形式、キーの割り当て、プラットフォームごとの差）
- 依存を足す・差し替える
- issue の受け入れ条件に書かれていない判断を、実装の都合で下した

**要らないもの**も同じ表に書く。バグ修正、文言、リファクタリング、受け入れ条件どおりの実装。

判定は**設計の段階**でする。`implement-issue` の「決めること」に入れ、設計コメントと PR 本文の両方に `## ADR` の欄を置く。

## 理由

- **完了条件に入れる理由。** このリポジトリで「必ずやること」が守られているのは、そこに並んでいるからで、文章で勧めているからではない。ADR だけ別の担保にする理由が無い
- **設計の段階で判定する理由。** 実装が終わってから振り返ると、「もう動いているものの説明」を書くことになる。代替案は実装前にしか正直に書けない。設計コメントを先に書く手順が既にあるので、そこに 1 欄足せば済む
- **要らない場合を明記する理由。** 何にでも書く運用にすると、読まれなくなる。読まれない記録は無いのと同じで、そのうえ書く手間だけ残る
- **判定を表にする理由。** 「重大」は人によって違う。例を並べて、同じ判定に落ちるようにする
- **`implement-issue` にも入れる理由。** 実際に手順を実行するのはこの skill で、**手順の中に無い決まりごとは呼ばれない**

## 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| 勧めるだけ（[#74](https://github.com/tokuhirom/ekanban/pull/74) の状態） | 書き忘れても何も落ちない。実際 #74 の時点で「いつ書くか」が無いまま放置されていた |
| すべての PR に ADR を要求する | 読まれなくなる。バグ修正 1 つに ADR が付く運用は、記録の価値を薄める |
| 「重大」の定義を書かず、判断に任せる | 人（とセッション）によって基準が変わる。同じ判断が ADR になったりならなかったりする |
| CI で機械的に検査する（`docs/DESIGN.md` の差分があれば ADR を必須にする、など） | 「重大な決定」は差分の形では判定できない。決まりごとを 1 行足しただけの PR と、方針を覆した PR を機械は区別しない。誤検知が増えると、通すための空の ADR が生まれる |
| `docs/DESIGN.md` に経緯も書く（ADR をやめる） | [#73](https://github.com/tokuhirom/ekanban/issues/73) で分けたばかりの判断を、理由が変わっていないのに戻すことになる |

## 結果

**良くなったこと。** ADR を書くかどうかが、issue を閉じる前の確認事項になった。判定は表で決まるので、人が変わっても同じ結論に落ちる。設計の段階で判定するので、代替案が実装前の形で残る。

**引き受けた不都合。**

- **完了条件が 10 項目になった。** 増やすほど 1 つずつの重みが下がる。これ以上足すなら、既存のどれかを畳むことも考える
- **判定は人（かエージェント）がやる。** 機械的には検査していないので、「要らない」と判断して書かなかったことを誰も咎めない。表の存在が、その判断を毎回同じ形にすることを期待している
- 表が古くなる可能性がある。判定の例は、実際の ADR が増えたら見直す
