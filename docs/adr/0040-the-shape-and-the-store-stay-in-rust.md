# 0040. 盤面の形と置き場所は Rust に残す

- 日付: 2026-09-08
- 状態: 有効
- 関連: [0039](0039-the-board-model-moves-to-typescript.md)、[0011](0011-due-counts-in-the-board-list.md)、[0018](0018-rust-owns-the-board-state.md)

## 状況

[0039](0039-the-board-model-moves-to-typescript.md) で盤面の**振る舞い**を TypeScript に移すと、次に決まるのは**形**をどちらが持つかである。`Board` / `Column` / `Card` / `Tag` / `ChecklistItem` のフィールドと、それを SQLite の行にどう落とすかのことである。

いまは形が Rust の構造体にあり、`ts-rs` が TypeScript の型を生成して `web/src/ipc/types/` にコミットし、CI が差分を見る（`make types-check`）。SQLite は関係スキーマ（スキーマ版 12）で、`db/mod.rs` の 1,310 行が読み込み・差分保存・移行を持つ。

形まで TypeScript に移すと、置き場所の側で行に落とすために Rust が同じ形をもう一度書くことになる。それを避けようとすると、盤面を JSON の 1 列にして Rust に形を知らせない、という道に行き着く。

## 決定

**形と置き場所は Rust に残す。SQLite のスキーマは変えない。**

- `crates/core/src/model.rs` に残るのは**データ定義だけ**——フィールドと `serde` / `ts-rs` の属性。採番・並べ替え・Undo・検索・期限・書き出しは [0039](0039-the-board-model-moves-to-typescript.md) のとおり TypeScript へ移る
- `ts-rs` による型の生成と `make types-check` は**そのまま続ける**。形が 2 か所に書かれない状態を、いまと同じ仕組みで保つ
- `db/mod.rs` はそのまま。SQL は `crates/core/src/db/` の中に残す（`AGENTS.md`）
- `save_board` は webview から受け取った `Board` を、いままでと同じ差分保存で書く。読み込みも移行もいまのまま
- **競合の検出のために `boards.rev` を足す**（列を 1 つ足すだけの移行、スキーマ版 13）。webview が持つ版と合わなければ書かずに `Conflict` を返す。呼んだ側が読み直す
- **受け取った盤面を検めてから書く。** 空のタイトル、知らないカラムやタグを指すカード、同じ `position` の重複や穴、ボードの名前空間から外れた ID、2^53 以上の ID。**盤面の判断をやり直すのではなく、整合だけを見る**——どこに落とすかを決めるのは webview で、そこで決まったものが行として成り立つかを見るのが置き場所である。多くはスキーマ（`NOT NULL`、外部キー、`UNIQUE`）が既に見ており、残りを保存の手前に置く
- **ID を数える器は盤面の中に置き、上限だけを置き場所が見る。** webview が手元で採番できないと、カードを 1 枚足すたびに往復が要る。番号の続きは盤面と一緒に保存され、`docs/DESIGN.md`「境界を越える値」の 2^53 の約束は保存のたびに Rust が確かめる

## 理由

**SQLite をやめる理由が無いから。** 差分保存もスキーマの移行も日次バックアップ（[0003](0003-daily-backup-generations.md)）も 1 プロセス 1 データベースのロック（[0004](0004-one-process-per-database.md)）も動いている。これは「TypeScript でも出来ること」ではなく、置き場所と OS の仕事である。[0039](0039-the-board-model-moves-to-typescript.md) が薄くしたいのは**盤面の判断が画面の外にあること**であって、置き場所ではない。

**形を 1 か所に保つ仕組みが既にあり、よく働いているから。** `ts-rs` の生成と CI の差分は、手で 2 か所に書けば必ずずれるという理由で入れたものである。振る舞いを移すことは、この仕組みをやめる理由にならない。

**データが不透明にならないから。** `sqlite3` から `SELECT * FROM cards` でカードを覗ける。ローカルのファイル 1 つで完結するアプリで、中身を自分の道具で読めることには値打ちがある。

**移行が要らないから。** 足すのは `rev` の列 1 つで、既存の行に触らない。データを作り直す移行は、それ自体がいちばん危ない作業である。

**検めるのはサーバの仕事だから。** ウェブアプリで、ブラウザが送ってきた JSON をそのままデータベースに書くサーバは書かない。ここでも同じで、置き場所は受け取ったものを信じない。ただし**検めることと、決め直すことは違う**——カードをどのカラムの何枚目に置くかは webview が決めたことで、置き場所はそれが行として成り立つかだけを見る。両方でやり直すと、[0018](0018-rust-owns-the-board-state.md) が避けたかった「写しが 2 つ」に戻る。

**`rev` が要る**のは、[0039](0039-the-board-model-moves-to-typescript.md) で盤面がプロセスに 1 つではなくなるからである。いままではボードの窓もキャプチャの窓も Rust の `AppState` 1 つを通っていたので、書き負けようが無かった。webview がそれぞれ手元に文書を持つと、キャプチャが足したカードを、ボードの窓の次の保存が黙って消せる。**黙って消えるのではなく `Conflict` として見える**形にする。

## 採らなかった案

- **ボードを JSON の 1 列にする（`boards(id, rev, data)`）。** Rust が盤面の形を一切知らずに済み、`db/mod.rs` は 1,310 行から 350 行前後になる見込みだった。**採らない。** 得るのは行数だけで、失うのは実データのほうである——`SELECT * FROM cards` ができなくなり、既存のデータベースを作り直す片道の移行が要り、期限の件数を SQL で数える [0011](0011-due-counts-in-the-board-list.md) の実装も書き直しになる。置き場所は、薄くしたいものの筆頭ではない
- **形も TypeScript に移し、Rust は行に落とすための構造体を手で持つ。** `ts-rs` が防いでいるずれが、防ぐ仕組みなしで戻ってくる。生成をやめて写しを 2 つ持つのは、いちばん悪い組み合わせである
- **`tauri-plugin-sql` で webview から SQL を書く。** [0018](0018-rust-owns-the-board-state.md) が断ったのと同じ理由。スキーマの移行、ファイルロック、日次バックアップは置き場所の側の仕事で、webview に持ち込むと OS の話が画面に混ざる
- **`rev` を持たず、`board:changed` を受けて読み直すだけにする。** イベントが届く前に保存すると書き負ける窓が残る。列 1 つで塞げるものを、タイミングに委ねる理由が無い

## 結果

得るもの。

- **データの見え方が変わらない。** 既存のデータベースはそのまま開き、`sqlite3` から読める。`docs/DEVELOPMENT.md` のスキーマの節も、`rev` の 1 行を足すだけで済む
- 形のずれを CI が見続ける。振る舞いだけが TypeScript に移り、境界を越える値の約束（`docs/DESIGN.md`「境界を越える値」）はそのまま残る
- Rust に残るものが「SQL と OS」で説明できるようになる
- 2 つの窓が同じボードを書く競合が、黙って消えるのではなく見える失敗になる

引き受ける不都合。

- **`model.rs` は消えない。** データ定義として 400 行前後が残る。**フィールドを 1 つ足すには Rust を触って `make types` を回すことになる**——振る舞いを変えるだけなら TypeScript で完結するが、形の変更は両方に届く
- **`ts-rs` と `make types-check` がビルドの前提として残る。** [0041](0041-one-layer-of-screen-tests.md) が e2e から Rust のビルドを外しても、型を触ったときは `cargo` が要る
- **検証が薄いと、壊れた盤面が書ける。** 検めるのは整合だけなので、「webview の側の論理が間違っていて、行としては成り立つ盤面」は素通りする。そこを守るのは TypeScript 側のテストで、置き場所の検証はその代わりにならない
- **差分保存の「自分の知らない行を消す」性質はそのまま残る。** `rev` はプロセスをまたぐ競合を見るものではない（そちらは [0004](0004-one-process-per-database.md) のファイルロックが引き受ける）
