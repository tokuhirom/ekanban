# 0029. IME の変換中かは 1 か所で判定し、`keyCode` も見る

- 日付: 2026-09-07
- 状態: 有効
- 関連: #124

## 状況

1 行の入力欄は `Enter` で保存し、`Escape` で取り消す（`docs/DESIGN.md`「画面の作り」）。
日本語を打つ人にとって、この 2 つは IME の確定と取り消しでもある。**変換を確定した
だけで保存されてはいけないし、変換を取り消しただけでパネルが閉じてもいけない。**

そのために各欄が `KeyboardEvent.isComposing` を見ていた。カードのタイトル欄も
見ていた。それでも、macOS でタイトルを打って変換を確定すると、そのままカードが
保存されてパネルが閉じた（#124）。

`isComposing` が当てにならないのは、**イベントの発火順がエンジンによって違う**
からである。Chromium は確定の `keydown` を先に出し、そのあとで `compositionend`
を出す。この順なら `keydown` の時点ではまだ変換中で、`isComposing` は `true` に
なる。WebKit は逆で、`compositionend` を先に出す。確定の `keydown` が届く頃には
変換は終わっており、`isComposing` は `false` である。

アプリが動く 3 つの webview のうち、macOS の WKWebView と Linux の WebKitGTK が
WebKit である（`docs/DESIGN.md`「テスト」）。つまり **3 つのうち 2 つで、
`isComposing` だけの判定はすり抜ける**。

判定はそのとき 11 か所に散らばっていた。同じ書き方が 11 個あり、そのうち 3 か所
（検索欄の `Escape`、プロンプトダイアログの `Enter`、ダイアログ背景の `Escape`）は
判定そのものが抜けていた。

## 決定

変換中かどうかの判定を **`web/src/shell/ime.ts` の `isComposing(event)` 1 つに
まとめ**、`KeyboardEvent.isComposing` を直に読むのをやめる。判定の中身は

```ts
event.isComposing || event.keyCode === 229
```

とする。`keydown` を受けて `Enter` / `Escape` / 矢印を取る場所は、すべてこの関数を
通す。直参照は ESLint の `no-restricted-syntax` で止め、例外は `shell/ime.ts` だけと
する。

`docs/DESIGN.md`「画面の作り」に、この判定を通すことを決まりごととして足す。

## 理由

**`keyCode` が 229 になるのは、発火順に左右されない唯一の目印だからである。**
229（`VK_PROCESSKEY`）は「このキーは IME が処理した」という意味で、実際に押された
キーは入っていない。変換に伴う `keydown` には、どのエンジンでもこれが載る。
`compositionend` が先に出ていても、その `keydown` が変換の一部だったことは
`keyCode` からは読める。

`keyCode` は非推奨である。それでも使うのは、代わりがないからである。`isComposing`
は仕様どおりに実装されていても発火順の差を吸収してくれず、`key` は確定の `Enter`
でも `"Enter"` としか名乗らない。非推奨のものを触る範囲を 1 ファイルに閉じ、
その 1 ファイルが DOM の型ではなく自前の型（`ComposingKey`）で受けることで、
lint を切らずに済ませる。

**判定を 1 か所にするのは、11 か所の同じ書き方が 11 通りに壊れるからである。**
今回すり抜けたのは全部が同じ理由だったのに、直す場所は 11 か所あった。抜けていた
3 か所も、同じ書き方を各自が書き写す運用だから抜けた。関数にすれば、次にエンジンの
差が見つかったときに直す場所は 1 つになる。ESLint で直参照を止めるのは、
TypeScript 側の規約を人の注意力ではなく道具に守らせると決めているためである
（`docs/DESIGN.md`「テスト」）。

## 採らなかった案

- **タイトル欄だけ直す。** issue に出ているのはタイトル欄だが、原因は共通で、
  同じ踏み方をする欄がほかに 10 個ある。1 か所だけ直せば、同じ issue が別の欄で
  もう一度立つ。
- **`compositionend` の時刻を各欄で覚え、その直後の `Enter` を捨てる。**
  `keyCode` を触らずに済むが、状態を持つ欄が 11 個に増え、「直後」が何ミリ秒かを
  決め打ちすることになる。速い打鍵で本物の `Enter` を捨てる側に倒れると、今度は
  保存されないという不具合になる。
- **`keydown` ではなく `keyup` で保存する。** 確定の `keydown` に続く `keyup` は
  変換の外なので見分けられるが、キーを押している間ずっと反応しない欄になり、
  ほかの割り当て（盤面の `Enter` でカードを開く）と噛み合わなくなる。
- **`key === "Process"` も見る。** Firefox と IE が IME 処理中のキーをこう名乗るが、
  この 3 つの webview はどれもそう名乗らない。動かないコードを持つことになる。

## 結果

変換の確定と取り消しが、保存とパネルの開閉に化けなくなった。判定の抜けていた
検索欄・ダイアログにも同じ判定が入った。

**この ADR が直したものを、ヘッドレステストは確かめられない。** Playwright は
本物の IME を打てないので、e2e が流しているのは「WebKit が確定のときに寄こす形」を
真似た合成イベントである。本物の IME での確認は実機に残る（`docs/DESIGN.md`
「変更の完了条件」6）。合成イベントが本物と同じ形かどうかは、そちらでしか
分からない。
