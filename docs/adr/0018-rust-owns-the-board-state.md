# 0018. 盤面の状態は Rust が持ち、webview は投影にする

- 日付: 2026-09-06
- 状態: 有効
- 関連: #97、[0017](0017-moving-the-ui-to-tauri.md)

## 状況

[0017](0017-moving-the-ui-to-tauri.md) で UI を Tauri へ移すと決めた。移した先で最初に決まるのは、**`Board` を誰が持つか**である。ここを決めないと、コマンドの形も、保存の仕方も、テストの置き場所も決まらない。

いまは `BoardView` が `Board` をメモリに持ち、操作のたびにモデルを変え、非同期で SQLite に書き、失敗したら巻き戻している。巻き戻しのために `PendingSave` / `ActiveSave` / `SaveFailure` の 3 つがあり、`SaveFailure` は「どのエディタを復元するか」で 6 分岐する。

webview 側で状態を持つなら、`model.rs` の 3,386 行——採番・並べ替え・Undo / Redo・アーカイブ・タグの整合——を TypeScript にもう 1 つ書くことになる。

## 決定

**`Board` は Rust 側の `State` が持ち、webview はその投影を描くだけにする。**

- 盤面を変えるコマンドは、**モデルへの適用と SQLite への保存を続けて行い、両方が成功してから**変更後のスナップショットを丸ごと返す。失敗したらモデルへの変更も捨てて `Err` を返す
- 差分は返さない。返すのは毎回スナップショット
- **確定していない入力（下書き）は webview が持つ。** タイトル、説明、タグ名、カラム名、検索語。確定した瞬間にコマンドを 1 回呼ぶ
- Undo / Redo のスタックは `Board` の中、つまり Rust 側に残る

## 理由

**中核を捨てないことが移行の前提だから。** [0017](0017-moving-the-ui-to-tauri.md) が「6,391 行はそのまま持っていく」と書いたのは、`model.rs` と `db/mod.rs` にテスト付きで積まれた論理のことである。状態を webview に持たせると、その論理の写しが webview 側にもう 1 つ生まれる。写しは必ずずれる。

**保存の失敗の扱いが 1 つに畳めるから。** 画面をまだ変えていない状態で失敗を返せるので、巻き戻すものが無い。`SaveFailure` の 6 分岐と 2 つのキューが消える。「画面には反映されているが SQLite には無い」という中間状態が、そもそも作れなくなる。

**スナップショットで足りるから。** ボードは数百枚のカードで、JSON にして数百 KB。操作は打鍵ごとではなく確定ごとにしか起きない。差分にすると適用の順序と欠落の面倒を webview で見ることになり、それは今回いちばん作りたくない部分である。

**下書きを Rust に置く理由が無いから。** IME の変換中の状態を IPC 越しに往復させても得るものが無く、`Escape` で捨てるだけのものを永続層の近くに置く必要も無い。副産物として「保存されていないカード」という状態（`discard_added_card` の経路）が消える。規則の意図——無題のカードを作らない、取り下げを `card_events` に残さない——は、経路が消えることで満たされる。

## 採らなかった案

- **webview が状態を持ち、Rust は保存だけを引き受ける。** `model.rs` の写しを TypeScript に作ることになる。Undo / Redo と採番と reindex を 2 か所で正しく保つのは、移行の費用としても、その後の保守としても高すぎる。「Rust の資産が消えない」という [0017](0017-moving-the-ui-to-tauri.md) の理由そのものが崩れる
- **差分（パッチ）を返す。** 帯域は減るが、順序・欠落・再送を webview 側で見ることになる。いまの規模で必要な最適化ではない。必要になったら、高頻度のコマンドだけ後から差分に落とせる（スナップショットを返す形は、その退路を塞がない）
- **いまと同じ非同期保存にし、webview に楽観的に先に描かせる。** 巻き戻しの 6 分岐が webview 側に移るだけで、何も減らない。ローカル SQLite の書き込みはミリ秒単位で、待てない相手ではない
- **`tauri-plugin-sql` で webview から SQL を書く。** スキーマ移行も差分保存も `db/mod.rs` にあり、SQL を UI から遠ざける方針（`AGENTS.md`）にも反する

## 結果

得るもの。モデルの真実が 1 つに保たれる。保存の失敗が 1 か所で終わる。中間状態が作れない。`view_tests.rs` が確かめていた「画面と SQLite の両方」のうち、モデル側はそのまま `cargo test` で確かめ続けられる。

引き受ける不都合。

- 盤面を変えるたびに IPC を 1 往復し、SQLite の書き込みを待つ。ドラッグ中のような連続した動きは webview 側で完結させ、確定の 1 回だけコマンドを呼ぶ設計が必要になる
- スナップショットの大きさが盤面に比例する。カードが増えたときの実測が要る
- 下書きが webview にあるので、**ウィンドウを閉じると下書きは消える**。いまも同じだが、境界がはっきりしたぶん、将来「下書きを残す」と決めたら Rust 側に持ち直す判断が要る
