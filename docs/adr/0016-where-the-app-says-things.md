# 0016. アプリが伝えることを、行き先ごとに分ける

- 日付: 2026-09-05
- 状態: 有効
- 関連: #86

## 状況

ヘッダのボード名の直下に、ステータス行が常時出ていた。ボード名の下・検索欄の上という一等地を占め、ボードを常に押し下げていた。

何も起きていないときに入るのは「● ローカル SQLite」というプレースホルダで、これは状態表示になっていなかった。

- ローカル SQLite で動くことは README にも「ekanbanについて」にも書いてある。使う人が選べる話ではないので、常に真の事実でしかない
- `●` は接続状態の印のように見えるが、何も監視していない。データベースが壊れていても開けなくても変わらない
- `status` を `None` に戻すコードが無く、この文字列が見えるのは起動直後から最初の操作までの間だけだった

そして、`set_info` / `set_success` / `set_error` の 66 箇所を中身で分けると、常時見える場所が要るのは 4 分の 1 だけだった。

| 種類 | 件数 |
| --- | --- |
| `set_info` の拒否・キャンセル・変更なし | 21 |
| `set_info` のその他（検索中、絞り込み解除など） | 15 |
| `set_success` | 10 |
| `set_error` | 20 |

常に何か出ていると人は読まなくなる。いちばん見逃されたら困る保存失敗が、いちばん見逃されやすくなっていた。保存に失敗すると `SaveFailure::Restore*` が編集内容を巻き戻すので、**黙って編集が取り消されたように見える**のがいちばん悪かった。

## 決定

ステータス行と `StatusMessage` / `StatusLevel` / `BoardView::status` / `set_status` / `set_info` / `set_success` / `set_error` を消し、伝えることを 3 つの行き先に分ける。

| 行き先 | 何を | 例 |
| --- | --- | --- |
| **ダイアログ** | 使う人が手を打たないと直らない失敗 | 保存の失敗、ボードの読み書きの失敗、書き出し・バックアップの失敗、ホットキーの登録失敗 |
| **ダイアログ**（唯一の成功） | アプリの外にファイルを書けたこと | 書き出し、データベースのコピー。パスを出し、そこを開く導線を付ける |
| **コントロールの無効化** | 押せるボタンがあるのに断られる操作 | 保存中・編集中のボード一覧と `＋`、空のカラムの「アーカイブ」 |
| **無言** | それ以外 | 拒否、キャンセル、変更なし、検索中、絞り込み解除、テーマ変更、「保存中…」 |

キーボードとメニューからしか来ない拒否は、無言で何もしない。

## 理由

**常時表示は、注意を配る仕組みとしては壊れている。** 何か出ているのが普通の状態になると、変わったことに気づけない。読まれなくなった行に載せられた保存失敗は、載っていないのと同じ。

**保存の失敗はダイアログでなければならない。** 失敗すると編集が巻き戻る。巻き戻したことを伝えないのは、使う人の入力を黙って捨てるのと変わらない。ダイアログは邪魔だが、邪魔なのが正しい場面がここ。`window.open_alert_dialog` は既にボード削除・アーカイブ・カラム削除で使っているので、仕組みも増えない。

**成功は原則として伝えない。** ローカル SQLite の単一ユーザーアプリで保存の成功を毎回報告するのは、アプリが自分の心配をしているだけで、使う人の役には立っていない。結果は画面に出ている。例外は書き出しとバックアップだけで、これはアプリの外にファイルができるので、画面のどこにも痕跡が残らない。

**拒否は、言葉ではなくコントロールで表す。** 「アーカイブ表示中はカードを追加できません」と言う必要が出ているのは、押せないはずのボタンが押せるから。押せなくすれば理由は要らない。押せるコントロールが無い経路（キーボード、メニュー）は、無言で何もしない。いまのメニューバーは静的な `menus()` から作るので、項目を状態で無効にする口がない（[ADR 0015](0015-a-menu-bar-on-every-platform.md)）。

**ダイアログは `defer` に載せて開く。** 保存の完了も書き出しも非同期で、そこに `&mut Window` は渡ってこない。`BoardView` にウィンドウのハンドルを持たせて引くが、gpui の `update_window` はウィンドウをスロットから取り出して更新するため、**同じウィンドウの更新中に呼ぶと取り出せず、黙って失敗する**。いまの更新が終わってから開けば、同期の経路でも非同期の経路でも 1 本の関数で済む。

## 採らなかった案

- **ステータス行を残して、出す内容だけ減らす。** 一等地を占め続ける理由が残らない。「たまに何か出る行」は、出ていないときの場所を無駄にする。
- **トースト（数秒で消える通知）にする。** 消えるものに保存失敗を載せると、席を外している間に消える。巻き戻ったことに気づけないという、いま直したい問題がそのまま残る。
- **失敗もヘッダに出したまま、色を強くする。** 読まれない場所の色を強くしても読まれない。#86 の数え上げが示すとおり、問題は目立ち方ではなく、常時表示そのものにある。
- **すべての拒否をダイアログにする。** 「変更はありません」でダイアログが出るアプリは使えない。確認ダイアログを Undo の代わりにしない、という既存の決まりごと（`docs/DESIGN.md`）と同じ理由で、出す先を絞らないと出すこと自体が効かなくなる。
- **ファイル選択をキャンセルしたときもダイアログを出す。** ダイアログを閉じたらダイアログが出る。

## 結果

ヘッダはボード名・検索欄・絞り込みノートだけになり、ボードが上に広がった。保存の失敗は必ず目に入るようになり、そのとき編集内容は編集パネルに戻る。

引き受けたのは、成功の手応えが無くなること。カードを保存しても何も出ない。画面が変わることがそのまま答えだという前提に乗っているので、画面に出ない変更を今後足すときは、この前提が成り立つか確かめる必要がある。

もう 1 つは、無効化されたコントロールが理由を言わないこと。押せない理由は、その場の状況（アーカイブ表示にいる、カラムが空）から読み取ってもらう形になった。読み取れない無効化を作らないことが、これからの制約になる。
