# 0011. 期限の件数を、ボード一覧の各行に出す

- 日付: 2026-09-05
- 状態: 有効
- 関連: #62

## 状況

期限は表示するだけで通知しない。[README の「やらないこと」](../../README.md)にも通知はスコープ外と書いてあり、この判断自体は変えていない。通知しないということは、**見に行かなければ気づけない**ということでもある。

複数ボードが入ったあと、見に行く先が増えた。検索も期限の表示もいま開いているボードの中で完結しているので、「期限切れのカードがどこかにあるか」にアプリが答えられない。ボード一覧は名前が並ぶだけで、中の状態を何も伝えていなかった。

[`docs/DESIGN.md`](../DESIGN.md) は「保存されたビュー（Perspective）」も「カレンダー / タイムラインビュー」も入れないと決めている。

## 決定

ボード一覧の各行に、そのボードの**期限切れ**と**本日期限**の件数を出す。

- 件数は `load_boards` の 1 クエリの中で SQL が数える。ボードごとに開いて数えない
- 開いているボードだけは、メモリ上の盤面から数える。保存が終わっていない編集も画面に出ているので、そちらと食い違わせない
- 畳んだ細い帯のときは、すべてのボードを合わせた印だけを出す
- 件数が 0 のものは出さない。両方 0 の行は名前だけになる

新しいビューは足さない。押したときの動きも今までどおりのボード切り替えのまま。

## 理由

**いま持っている情報を、既にある画面に出すだけ。** 期限は既にデータとして持っていて、ボード一覧は既に画面にある。足したのは行の中の 1 行で、画面も概念も増えていない。却下してある Perspective やカレンダーは、どちらも新しいビューを作る案だった。ここはそれに当たらない。

**数えるのは SQL の仕事。** アプリ側で数えるにはボードを 1 つずつ読み込むことになり、ボードが増えるほど一覧が重くなる。`LEFT JOIN` と `SUM(CASE ...)` なら、ボードが何枚あってもクエリは 1 回で済む。期限は `'YYYY-MM-DD'` の `TEXT` なので、文字列の比較がそのまま日付の前後になる。

**開いているボードだけメモリから数えるのは、画面との食い違いを避けるため。** 期限を今つけたカードが、一覧の件数にだけ反映されないのは説明できない。保存が終わるのを待って数え直すより、その場で数えるほうが単純で、枚数も高々そのボードの分しかない。

**色だけに意味を持たせない**（`docs/DESIGN.md`）ので、数の隣に「期限切れ」「今日」と書く。記号（`⚠` `◷`）も添えるが、記号だけにも頼らない。

## 採らなかった案

- **全ボードを横断する「今日やること」のビューを作る。** 新しいビューが 1 つ増える。ボード一覧という「どこを見に行くか」を選ぶ画面が既にあるのに、その隣にもう 1 つ選ぶ場所を作ることになる。D&D の落とし先が二重になるという、カレンダービューを却下したのと同じ問題も持ち込む。
- **OS の通知を出す。** README の「やらないこと」。判断は変わっていない。
- **件数ではなく色の点だけを出す。** 「色だけに意味を持たせない」に反する。何件あるかも、どちらの種類かも読めない。
- **期限が近い（`Soon`）ものまで数える。** 出すものが増えるほど、どれも見られなくなる。行動が変わるのは「過ぎている」と「今日」の 2 つで、その先は開いて見ればいい。
- **一覧を開くたびに全ボードをアプリ側で読み込んで数える。** 受け入れ条件が明示的に禁じている。

## 結果

ボードを開かなくても、どのボードを見に行くべきかが分かるようになった。

引き受けたのは、開いていないボードの件数が「最後に一覧を読んだ時点」のものであること。日付が変わっても、一覧を読み直すまでは前日の基準で数えた値が出る。ボードを切り替えるときに離れるボードの件数を書き戻し、削除や起動時には読み直すので、実際に古くなるのは「アプリを開いたまま日をまたぎ、ボードも切り替えない」場合に限られる。そこまで追うには一覧を定期的に数え直すことになり、通知を入れないという判断と釣り合わない。
