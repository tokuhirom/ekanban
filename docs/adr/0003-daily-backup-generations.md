# 0003. 自動バックアップの世代を、起動ごとではなく日ごとに刻む

- 日付: 2026-09-05
- 状態: 有効
- 関連: [#63](https://github.com/tokuhirom/ekanban/issues/63) [#64](https://github.com/tokuhirom/ekanban/pull/64)

## 状況

データを守る仕組みが 2 つしかなかった。Undo はセッション限りで、アプリを終了すると消える。「データベースをコピー…」は人が思い出して手で取るもの。そのため「カラムを消した状態で終了した」「ファイルが壊れた」のどれも戻す先が無かった。ローカルの 1 ファイルが唯一の正本になっている。

控えを作る手段（`VACUUM INTO` を使う `Database::backup_to`）は既にあり、自動で呼ぶ経路が無いだけだった。

issue の案は「**起動時に世代付きのコピーを 1 つ作り、決めた世代数だけ残す**」。

## 決定

控えは**日付をファイル名に入れて、1 日 1 つ**取る（`ekanban-2026-09-05.sqlite3`）。その日のファイルが既にあれば取らない。日付の新しい順に 7 世代だけ残す。

取るのは**起動時**。書き込みは `.part` に対して行い、完了してから `rename` する。

## 理由

**起動ごとに刻むと、バックアップが一番要る場面でローテーションが正本を食う。**

```
カラムを消してしまう
 → 「あれ？」と思って再起動        → 壊れた状態の控えが 1 つ積まれる
 → もう一度確かめようと再起動      → 2 つ目
 → まだ確かめる                    → 3 つ目
```

7 世代なら、これを数回繰り返すだけで無事だった世代が押し出される。

日付で刻めば、同じ日に何度起動しても残るのは**その日の最初の 1 回**、つまりまだ壊していない状態になる。前の日のぶんも無傷のまま残る。おまけに「前回から変わったか」を持ち回る状態管理が要らず、ファイルの有無だけで決まる。

**起動時であって終了時でない理由。** 終了時に取ると、壊した状態のほうを保存することになる。

**`.part` に書いてから rename する理由。** 途中でアプリが終わっても、中途半端なファイルが世代として残らない。

**世代の判定にファイル名の日付を使い、mtime を見ない理由。** ファイルをコピーすると mtime は当てにならない。名前から読めるほうが、テストでも人の目でも決定的になる。

## 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| 起動ごとに 1 世代（issue の原案） | 上記のとおり、壊したあとの再起動で無事な世代が消える |
| 内容が変わったときだけ取る | ハッシュか mtime を `app_state` に持ち回る必要がある。日付方式なら状態を持たずに同じ効果が出る |
| アプリ内からの復元 UI | 開いているボードの破棄、保存中の待ち合わせ、失敗時のロールバック、Undo スタックの扱いが要る。戻す作業は年に数回で、そのために常時抱える複雑さに見合わない。控えはデータベースと同じ形式の 1 ファイルなので、終了してファイルを上書きすれば戻る |
| 成功を画面に出す | 起動のたびに必ず起こることを通知に出すと、通知そのものが読まれなくなる。失敗だけログに残す |

## 結果

**良くなったこと。** 起動するだけで 7 日ぶんの戻り先ができた。壊したあとに何度再起動しても、その日の朝の状態は残る。

**引き受けた不都合。**

- **粒度は 1 日**。今日足したカードを今日壊したら、今日ぶんは戻らない
- `backups/` はデータベースと同じディレクトリにある。**ディスク障害や誤ったディレクトリ削除からは守れない**。守るのは人的ミスとアプリのバグまで。持ち出し先の管理を始めるとクラウド同期の設計になり、README の「やらないこと」に入る
- 戻す操作は手動（アプリを終了 → ファイルを上書き）。手順は `docs/MANUAL.md` にある
