# 0005. ネイティブのメニューバーが無い環境では、画面の中にメニューを出す

- 日付: 2026-09-05
- 状態: 置き換えられた（→ [0015](0015-a-menu-bar-on-every-platform.md)）
- 関連: [#42](https://github.com/tokuhirom/ekanban/issues/42) [#47](https://github.com/tokuhirom/ekanban/pull/47)、[#54](https://github.com/tokuhirom/ekanban/issues/54) [#65](https://github.com/tokuhirom/ekanban/pull/65)、[#49](https://github.com/tokuhirom/ekanban/issues/49) [#69](https://github.com/tokuhirom/ekanban/pull/69)

## 状況

`cx.set_menus` が実際にメニューバーを出すのは **macOS だけ**で、Linux と Windows では何もしない。そのため「メニューに畳んだ操作」がその 2 つの環境では到達不能になり、到達させるために画面へ常時出すしかなくなっていた。サイドバーに「名前を変更」「ボードを削除」のボタンが並んでいたのがそれで、`docs/DESIGN.md` の「常用しない操作を画面に常時出さない」と真正面からぶつかっていた。

同じ根を持つ問題が続けて 3 つ出た。

- メニューバーが無いので操作が画面に溢れる（#42）
- macOS では最後のウィンドウを閉じてもプロセスが残るのに、Dock から開き直す受け口が無い（#54）
- GNOME の Wayland では枠もタイトルバーも出ない（#49）

## 決定

**プラットフォームごとに、その環境で素直な形にする。** 共通の見た目に寄せない。

| 環境 | メニュー | ウィンドウの枠 |
| --- | --- | --- |
| macOS | ネイティブのメニューバー | OS が描く。`Cmd+W` のあとは `Application::on_reopen` で Dock から戻す |
| Linux / Windows | ヘッダ右端の `≡` | ふつうは WM が描く。装飾を寄越さない環境（GNOME の Wayland）では自分で描く |

判定は **OS 名ではなく能力**で行う。枠は `window.window_decorations()` が `Decorations::Client` かどうかで見る。「Wayland かどうか」では見ない。X11 でも装飾を寄越さない構成はありえ、Wayland でも Mutter 以外は寄越す。

画面内メニューの項目は `src/menu.rs` にメニューバーと**並べて**置き、押したときは**メニューバーと同じアクションを投げる**。

## 理由

- **同じアクションを投げる理由。** 項目ごとに `BoardView` のメソッドを直接呼ぶと、メニューバー経由と `≡` 経由で挙動がずれる余地ができる。`window.dispatch_action` なら経路は 1 本で、操作の実体は `on_action` の 1 か所に残る
- **項目を同じファイルに置く理由。** 片方にだけ項目が増えたらテストで落とせる（`menu::tests::offers_every_menu_bar_action_in_the_app_menu`）
- **macOS に `≡` を出さない理由。** ネイティブのメニューバーと二重になるだけで、たどれる操作は増えない
- **開き直すときに状態を DB から読み直す理由。** ウィンドウを閉じている間もクイックキャプチャはカードを足せる。閉じたときのメモリ上の値で開き直すと古い盤面が出る

## 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| `≡` を全プラットフォームで出す | macOS でネイティブのメニューバーと二重になる。1 つの画面に寄せる利点より、各環境で素直であるほうを採った |
| gpui-component の `TitleBar` を使う | `TitleBar::window_options()` が `appears_transparent` と信号機ボタンの位置を要求し、**macOS の見た目が変わる**。枠を出したいのは装飾を寄越さない環境だけなので、そのために全環境の見た目を動かさない |
| 縁とリサイズを自前で書く | 辺の当たり判定はタイル配置（`Tiling`）で辺ごとに変わる。自前だとスナップ時に存在しない縁を掴もうとする。gpui-component の `window_border()`（Zed 由来）に任せた |
| 「ウインドウを開く」メニュー項目を足す（#54） | Dock から戻れれば足りる。項目を足すと「ウィンドウは 1 つ」の前提と、二重に開かない制御が別途要る |
| `≡` に「しまう」「拡大／縮小」も出す | macOS のウィンドウ操作。ほかの環境では WM の仕事で、アプリのメニューに出す意味がない |

## 結果

**良くなったこと。** サイドバーから常時表示のボタンが消え、「常用しない操作を画面に常時出さない」に戻れた。Linux / Windows からも書き出し・バックアップ・テーマ・タグ整理に手が届く。macOS では `Cmd+W` のあと Dock で戻り、`Cmd+M` が効く。GNOME の Wayland でウィンドウを動かせる。

**引き受けた不都合。**

- **画面がプラットフォームで分岐する。** `docs/MANUAL.md` のスクリーンショットは Linux で撮っているので、macOS では `≡` が写っていない旨の但し書きが要る
- **macOS 側の分岐は CI で動かない**（CI は Linux）。これが [0006](0006-ci-on-three-platforms.md) の直接のきっかけになった
- Wayland の枠は**ヘッドレスでは一切踏めない**。GPUI のテスト用プラットフォームは `window_decorations()` に `Decorations::Server` を返すので、テストが通るのは「装飾が Server のとき今までと変わらない」側だけ
- Wayland ではウィンドウの**位置**が復元されない。クライアントが自分の画面上の位置を知ることも指定することもできないため、アプリ側では直せない。大きさだけが戻る
