# 0043. メニューの構成を webview が持ち、Rust は組み立てだけを引き受ける

- 日付: 2026-09-08
- 状態: 草案（未確定）
- 関連: [0015](0015-a-menu-bar-on-every-platform.md)、[0030](0030-capturing-a-shortcut-needs-the-menu-out-of-the-way.md)、[0039](0039-the-board-model-moves-to-typescript.md)

## 状況

`crates/app/src/menu.rs` は 1,257 行（うちテスト 439 行）で、その大半は**何がどう並ぶか**である。押されたときの意味は既に webview にある——盤面・下書き・表示の状態に触る項目は `AppAction` として `app:action` で webview に投げ返され、`web/src/shell/actions.ts` の 1 本の dispatcher が実行する（`docs/DESIGN.md`「メニューとキー割り当て」）。Rust が自分で行うのは `WindowAction`（閉じる、終了、フルスクリーン）だけである。

**つまり、構成だけが Rust にあり、意味は webview にある。** メニュー項目を 1 つ足すには、`menu.rs` に並びを書き、`AppAction` を足し、生成された型を通して `actions.ts` に行き先を書く。3 か所を触る。

[0039](0039-the-board-model-moves-to-typescript.md) で型の生成をやめると、この往復はさらに手で写す作業になる。

## 決定

**メニューの構成を TypeScript が持ち、起動直後に Rust へ渡す。**

- 構成データ（節・項目・区切り・アクセラレータ・有効無効・プラットフォームごとの並びの違い）は `web/src/shell/menu.ts` にある
- webview は起動の最初に `set_menu(sections)` を 1 回呼ぶ。Rust はそれを Tauri のメニューに変換して掛けるだけになる。押されたら、いままでどおり `app:action` を投げ返す
- **起動時、webview が繋がるまでは最小限のメニューだけを Rust が置く。** macOS は OS が要求するアプリメニュー、ほかは空のバー
- どの OS かは Rust が渡す（`StartupState.platform`）。[0009](0009-per-platform-key-bindings.md) のとおり `navigator.userAgent` は見ない
- アクセラレータの付け外し（[0030](0030-capturing-a-shortcut-needs-the-menu-out-of-the-way.md)）は、webview が構成を組み直して渡し直す形になる。**控えを持たず組み直す**という 0030 の決定はそのまま

## 理由

**サーバ側に書くものではないから。** [0039](0039-the-board-model-moves-to-typescript.md) の線引き——ウェブアプリとして作ったならサーバに書いただろうものだけを Rust に置く——で見ると、メニューはサーバに無い。ウェブアプリなら画面の中に描いていたもので、ここでそれを OS に描かせているのは、殻を自分で持っているからにすぎない。**描く相手が OS であることは、構成を Rust に置く理由にならない。**

**意味のあるところに構成を置くから。** 何が並ぶかは画面の話で、押されたときに何が起きるかは既に画面にある。1 つにすれば、メニュー項目を足すのに触るのは 1 か所になる。

**テストが構成と実行を同じところで書けるから。** いまは `menu.rs` のテストが並びを見て、Playwright が実行を見ている。同じ場所に置けば、「メニューにあるのに行き先が無い」を 1 つのテストで捕まえられる。

**`cfg!` を構成の途中に置かない**という `docs/DESIGN.md` の規則は、TypeScript ではもっと自然に守れる。プラットフォームは引数なので、両方の並びを常に組み立てられる形にしかならない。

## 採らなかった案

- **構成を Rust に残す。** [0039](0039-the-board-model-moves-to-typescript.md) を通したあとも、メニュー項目 1 つのために Rust と TypeScript の両方を触る状態が続く。型の生成をやめたぶん、その写しは手で保つことになる
- **メニューを webview の中に描く。** [0015](0015-a-menu-bar-on-every-platform.md) が「どのプラットフォームでも OS が描くメニューバーを出す」と決めている。これを覆す理由は無い
- **`set_menu` を使わず、Rust が起動時に構成を組んでから webview を開く。** 構成を Rust に置くのと同じことになる

## 結果

得るもの。`menu.rs` は 1,257 行から 250 行前後（変換とアクセラレータの表記）の見込みになる。メニュー項目を足すのに触るのが 1 か所になる。

引き受ける不都合。

- **起動直後のごく短い間、メニューが最小限になる。** webview が最初のコマンドを呼ぶまでの数百ミリ秒である。macOS では「アプリメニューが一瞬だけ短い」ことになる。**これが目に見えて不格好なら、この決定は取り下げる**——確かめるまで、これは見込みでしかない
- **メニューの構成が、webview の起動失敗に巻き込まれる。** webview が上がらなければメニューも最小限のまま残る。もっとも、そのときは画面も出ていない（`docs/DESIGN.md`「起動できないと分かっているなら、ウィンドウを開かない」）
