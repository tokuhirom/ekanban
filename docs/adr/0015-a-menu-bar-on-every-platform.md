# 0015. どのプラットフォームでもメニューバーを出す

- 日付: 2026-09-06
- 状態: 有効
- 関連: [#79](https://github.com/tokuhirom/ekanban/issues/79)、[0005](0005-in-app-menu-without-a-menu-bar.md) を置き換える

## 状況

[0005](0005-in-app-menu-without-a-menu-bar.md) は「ネイティブのメニューバーが無い環境では、画面の中にメニューを出す」と決め、Linux と Windows ではヘッダ右端の `≡` から 1 枚もののリストを出していた。到達不能な操作は無くなったが、2 つ残った。

- **項目の定義が二重。** `menus()`（メニューバー）と `app_menu()`（`≡`）が同じ操作を別々に持ち、`menu::tests::offers_every_menu_bar_action_in_the_app_menu` が整合を見張っていた。テストがあるのは、放っておくとずれるからである
- **メニューバーの作法が無い。** クリックで開く、開いている間はほかのメニュー名にホバーすると切り替わる、`←` `→` でメニューを移動する、項目の右にショートカットが出る──VS Code や Zed が Linux・Windows でやっていることが、`≡` では 1 つも成り立たない

`≡` を選んだのは、当時「メニューバーを自分で描く」のが相応の実装量に見えたからだった。実際には gpui-kit 側に部品が揃っていた。

## 決定

**どのプラットフォームでもメニューバーを出す。** macOS は OS に描かせ、Linux と Windows は `gpui_kit::component::menu::AppMenuBar` で自分で描く。`≡` は廃止する。

| 環境 | メニュー |
| --- | --- |
| macOS | `cx.set_menus` が作るネイティブのメニューバー |
| Linux / Windows | `AppMenuBar` を、（自分で描くときは）タイトルバーの下に 1 行 |

**メニューの構成は OS ごとに分ける。** `macos_menus()` と `drawn_menus()` を `cfg` 無しで定義し、`menus()` が `cfg!` で選ぶ。macOS 以外では「終了」を ファイル に、「ekanbanについて」とクイックキャプチャの設定を ヘルプ に移し、サービス・隠す・すべてを表示・しまう・拡大／縮小は出さない。

**`AppMenuBar` へは `menus()` をもう一度組んで渡す。** `AppMenuBar` が読むのは `gpui_base::GlobalState::app_menus` で、`cx.set_menus` はそこまで運ばない。

**ボードは開いた時点でフォーカスを持つ。**

## 理由

- **`AppMenuBar` を使う理由。** クリックで開く・ホバーで切り替え・`Esc` で閉じて元のフォーカスへ戻す・`←` `→` でメニュー移動、下の `PopupMenu` が `↑` `↓` `Enter`・区切り線・サブメニュー・無効項目・ショートカットの右寄せ表示（`Kbd`）・20 項目超のスクロールを持つ。キー割り当ては `gpui_kit::init` が入れる。自分で書く部分は、ボードの見た目に合わせた枠だけになる
- **`OwnedMenuItem::SystemMenu` は `PopupMenu` が読み飛ばす。** macOS の「サービス」が非 macOS に漏れる心配が要らない
- **構成を OS ごとに分ける理由。** 1 本の定義を描画時にフィルタすると、「どこに何が出るか」がビューのフィルタ条件に散る。分ければ、それぞれの構成をそのまま読める。`cfg` を付けずに両方定義するのは、**どの OS の CI でも両方を突き合わせられる**ようにするため。macOS 分岐は CI（Linux）で動かないという [0006](0006-ci-on-three-platforms.md) の悩みを、この 1 点については回避できる
- **`cx.get_menus()` で読み返さない理由。** しまうかどうかがプラットフォーム任せで、テストのプラットフォームは何も返さない。読み返す実装にすると、テストでは空のメニューバーになる（実際にそうなり、`hands_the_menu_definitions_to_the_menu_bar` が落ちた）
- **ボードにフォーカスを渡す理由。** ショートカットもメニューの項目も `"Board"` の文脈にぶら下がっている。どこにもフォーカスが無いと、メニューから飛ばしたアクションが誰にも届かず、**押しても何も起きない**。ショートカットの表示も同じ文脈から引くので、出るのはフォーカスが載ってからになる。`≡` は開くたびにボードへフォーカスを戻していたが、メニューバーは別の部品で、そこに手を入れる場所がない

## 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| Linux で本物の「OS のメニューバー」を出す | X11 にも Wayland にもメニューという層が無い。GTK も Qt もウィンドウの中に描いている。外に出る仕組みは KDE Plasma と Unity の Global Menu（`com.canonical.dbusmenu` と `_KDE_NET_WM_APPMENU_OBJECT_PATH`）だけで、gpui に実装は無く、**GNOME は 3.32 でアプリメニューを廃止しているので出す場所すら無い** |
| Windows で Win32 の `SetMenu` を使う | 本物のメニューバーは作れるが、`WM_COMMAND` を受けるにはウィンドウプロシージャが要り、それは gpui が握っている。`SetWindowSubclass` でしか割り込めず噛み合わせは無保証。`unsafe_code = "forbid"` も曲げることになる。見た目もシステム色固定でダークモードに追従しない。VS Code も Zed も Windows Terminal も自前描画である |
| メニューバーをタイトルバーの行に入れる（VS Code のカスタムタイトルバー相当） | `AppMenuBar` は `size_full()` と `overflow_x_scroll()` を持つので、`flex_none` の行に入れると幅の解決が循環する。装飾が Server か Client かで置き場所が変わるのも避けたい。1 行を独立させれば、どちらでも同じに置ける |
| 定義を 1 本にして描画時にフィルタ | 「どこに何が出るか」がビューのフィルタ条件に散る。分岐は定義側に置いた |
| `≡` を狭いウィンドウ用に残す（VS Code の compact menu bar） | 5 つのメニュー名は狭い窓でも収まる。`AppMenuBar` 自身が横スクロールを持つので、溢れても手は届く |
| Alt によるニーモニック（`Alt+F` で ファイル） | Windows の作法としては正統だが、`AppMenuBar` に無く、gpui のキー処理と Alt の握り合いが要る。**まず本体を入れて、必要になったら足す** |

## 結果

**良くなったこと。** メニュー項目の定義が 1 か所になり、整合を見張るテストが要らなくなった。Linux と Windows で、VS Code や Zed と同じ手つきでメニューを使える。ショートカットが項目の右に出るので、覚える手がかりが増えた。ボードが最初からフォーカスを持つので、起動直後に `Ctrl+N` が効く（以前は一度ボードをクリックする必要があった）。

**引き受けた不都合。**

- **メニューバーが 1 行ぶん場所を取る。** `≡` はヘッダに間借りしていた。装飾を自分で描く環境（GNOME の Wayland）では、タイトルバー 32px と合わせて 62px になる
- **ボードの `…` や右クリックのメニューと、メニューバーが互いを知らない。** `AppMenuBar` は独立した部品で、閉じる指示を外から出せない。メニューバーを触ったときにボード側を畳む（`dismiss_board_menus`）ことでしのいでいるが、逆向き（ボードのメニューを開いてもメニューバーは閉じない）は残っている
- **ヘッドレスのテストで見られるのは、定義が `GlobalState` に届いているかまで。** 開く・ホバーで切り替わる・`Esc` で閉じるは `AppMenuBar` の内部状態で、外から読めない。この PR では仮想ディスプレイ（Xvfb）上で目視した
- **`docs/MANUAL.md` のスクリーンショットが古くなる。** `≡` は写っていない
